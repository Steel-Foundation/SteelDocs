Steel 發佈嘅首份基準測試聚焦於佢目前最擅長嘅工作： **地形生成**。我哋將原生編譯嘅 Steel 伺服器與搭載 [Chunky](https://modrinth.com/plugin/chunky) 預生成插件嘅 Fabric 伺服器進行咗對比。

:::note[以 Fabric 作為原版基準線]
喺本頁所有測試入面，**Fabric**均代表安裝咗 Fabric Loader、Fabric API 與 Chunky，但**未安裝任何效能優化模組**嘅 Minecraft Java 版 26.2 伺服器。我哋將其作為可重複自動執行嘅原版（Vanilla）對照基準：Chunky 僅負責劃定固定嘅預生成區域並調度工作，實際嘅區塊生成完全由 Minecraft 原版世界生成器完成。
:::

喺呢部測試機器上面，三次重複測試中 Steel 生成 10,201 個測試區塊嘅速度係**Fabric 嘅 18.8 倍**。

| 伺服器 | 中位數耗時 |     平均吞吐量 | 中位數峰值常駐記憶體 (RSS) | 平均 CPU 佔用 |
| ------ | ---------: | -------------: | -------------------------: | ------------: |
| Steel  |     3.95 s | 2,581.8 區塊/s |                   1.79 GiB |     30.2 核心 |
| Fabric |    74.42 s |   137.2 區塊/s |                   2.47 GiB |      4.4 核心 |

耗時與記憶體數據取三次運行嘅中位數（Median），吞吐量與 CPU 佔用取算術平均數（Mean）。吞吐量越高越好，耗時與記憶體佔用越低越好。

![展示三次冷啟動測試平均區塊生成吞吐量嘅水平棒形圖：Steel 為 2,581.8 區塊/秒，Fabric 為 137.2 區塊/秒。](@/assets/benchmarks/chunk-generation-throughput.svg)

多核並行擴展能力係呢個差距嘅重要原因：喺測量區間內，Steel 平均令 30.2 個邏輯 CPU 核心保持滿載運作，而 Fabric 平均僅佔用咗 4.4 個核心。

![展示平均 CPU 核心佔用數嘅水平棒形圖：Steel 為 30.2 核心，Fabric 為 4.4 核心。](@/assets/benchmarks/chunk-generation-cpu.svg)

### 按 CPU 核心時間折算歸一化

將吞吐量除以平均 CPU 佔用核心數，可以粗略衡量每個 CPU 秒（CPU-second）完成嘅區塊生成工作量：

| 伺服器 | 每 CPU 秒生成區塊數 | 相對 Fabric 倍率 |
| ------ | ------------------: | ---------------: |
| Steel  |               85.51 |            2.75× |
| Fabric |               31.15 |            1.00× |

經過 CPU 核心數折算後差距有所收窄，但依然顯著：**Steel 每 CPU 秒生成嘅區塊數約為 Fabric 嘅 2.75 倍**。當然，單核效率並唔能夠取代真實掛鐘時間（Wall-clock）吞吐量——閒置嘅 CPU 核心並唔能夠令預生成任務提早行完——但呢項指標令我哋喺觀察多核並行擴展性之餘，亦可以直觀睇到單核執行效率嘅提升。

## 記憶體佔用

喺今次測試入面，Steel 嘅峰值常駐記憶體（Peak RSS）同樣較低：其中位數峰值為**1.79 GiB**，而 Fabric 為**2.47 GiB**。

下方折線圖展示咗各伺服器中位數耗時嗰一次運行期間嘅記憶體變化。曲線提早結束代表該伺服器已經提早完成咗全部區塊生成任務，而非記憶體跌到零。

![隨時間變化嘅常駐記憶體（RSS）折線圖：Steel 喺約 4.0 秒、1.8 GiB 附近完成生成，而 Fabric 喺約 74.4 秒、3.6 GiB 附近完成生成。](@/assets/benchmarks/chunk-generation-memory.svg)

常駐記憶體集大小（RSS）測量嘅係成個伺服器進程佔用嘅物理記憶體，而唔單止係活動區塊數據：對於 Java 而言，呢個數值包含咗 JVM 自身及已提交嘅堆記憶體頁（Committed Heap Pages）；對於 Steel 而言，則包含原生進程與記憶體分配器開銷。該指標反映咗作業系統喺此負載下實際駐留嘅記憶體大小，但並唔能直接等同於 Java 堆內活動物件與 Rust 記憶體分配量嘅對比。

## 更大區域擴展性測試（301×301）

我哋仲對每個伺服器各運行咗一次**301×301 區塊區域**（共**90,601 個區塊**，面積為 101×101 測試嘅 8.88 倍）嘅生成測試。更大嘅區域可以令調度器與線程池充分預熱（Warm up），更能體現持續穩定吞吐量；不過單次運行嘅統計置信度不及重複三次嘅 101×101 測試。

| 伺服器 |    耗時 |         吞吐量 | 峰值 RSS | 平均 CPU 佔用 | 每 CPU 秒生成區塊數 |
| ------ | ------: | -------------: | -------: | ------------: | ------------------: |
| Steel  | 32.14 s | 2,818.6 區塊/s | 3.98 GiB |     29.4 核心 |               95.86 |
| Fabric | 8:37.39 |   175.1 區塊/s | 3.35 GiB |      4.1 核心 |               42.68 |

喺呢次大區域運行入面，**Steel 嘅速度係 Fabric 嘅 16.10 倍**；按平均 CPU 佔用核心數折算後，**Steel 每 CPU 秒完成嘅區塊數係 Fabric 嘅 2.25 倍**。

喺更大區域下，兩個伺服器嘅平均吞吐量相較各自嘅 101×101 均值都有所提升：Steel 提升咗 9.2%，Fabric 提升咗 27.6%。由於大區域測試喺記憶體入面保留咗更多已生成及待處理嘅區塊數據，唔同區域尺寸之間嘅峰值 RSS 唔適宜直接橫向比較。

![對比 Steel 與 Fabric 喺 101×101 三次均值與 301×301 單次運行下區塊生成吞吐量嘅分組水平棒形圖。](@/assets/benchmarks/chunk-generation-scaling.svg)

## 測試方法論

主基準測試圍繞區塊座標 `(0, 0)` 生成一片全新嘅**101×101**完整主世界（Overworld）區塊正方形區域，共計**10,201 個目標區塊**（約合 2.61 平方公里）。擴展性測試則使用**301×301**正方形區域，共計**90,601 個目標區塊**（約合 23.19 平方公里）。所有測試均使用以下固定世界種子碼：

```text
8500081009970950196
```

之所以選用呢個種子碼，係因為佢具有極高密度嘅生態與地形多樣性：該種子碼嘅發現者[報告稱喺距離原點 (0, 0) 1,000 格範圍內涵蓋咗幾乎所有生物群系與結構](https://www.reddit.com/r/minecraftseeds/comments/1tf9iz2/ive_been_seedfinding_for_close_to_3_years_now/)，從而可以喺緊湊嘅測試區域內廣泛覆蓋各類地形與結構生成邏輯。

雙方嘅公共測試條件如下：

- Minecraft Java 版 26.2
- 啟用結構（Structures）生成
- 無玩家連接
- 每次運行均使用全新嘅空白世界目錄
- 世界存檔目錄掛載喺同一個 `tmpfs` 記憶體檔案系統上
- 每個伺服器喺 101×101 規模下執行三次冷啟動運行，喺 301×301 規模下執行一次冷啟動運行
- 每 250 毫秒採樣一次進程 CPU 時間與常駐記憶體（RSS）
- Steel 預生成並行窗口設為 64 區塊（`PREGEN_WINDOW_SIZE=64`）

將世界存檔放喺 `tmpfs` 上係為咗剔除物理磁碟 I/O 瓶頸嘅干擾——區塊序列化、Zlib 壓縮與檔案寫入調用依然照常執行，但物理硬碟讀寫速度唔會掩蓋 CPU 生成管線本身嘅表現。

Steel 嘅計時起點為日誌輸出 `Preparing spawn area`，終點為 `Spawn area prepared`；Fabric 嘅計時起點為 Chunky 輸出 `Task started`，終點為 `Task finished`。進程啟動、註冊表載入、出生點選取以及熄服退出均唔包含喺測量計時區間內。

### 點樣重現基準測試

基準測試驅動腳本與圖表渲染器均已作為 TypeScript 腳本收錄喺本倉庫入面，使用 Bun 運行。喺文檔倉庫根目錄下執行：

```sh
PREGEN_WINDOW_SIZE=64 bun run benchmark -- \
  --steel ../SteelMC \
  --fabric ../fabric_server \
  --output /tmp/steel-benchmark \
  --runs 3 --side 101
```

如需運行單次大區域擴展測試，只需要將最後一行改為 `--runs 1 --side 301` 並指定另一個輸出目錄。

測試運行器會喺每次試驗前建立全新嘅臨時世界目錄、透過 SHA-512 驗證固定版本嘅 Chunky 與 Fabric API、採集 Linux `/proc` 指標，並輸出原始日誌及 JSON / CSV 結果檔案。預設嘅 `all` 設定會喺每次試驗間交替輪換 Steel 與 Fabric 嘅執行先後順序；亦可以使用 `--profile steel` 或 `--profile fabric` 單獨測試其中一個伺服器。

若要根據倉庫中保存嘅原始測試數據重新渲染 SVG 圖表，可以運行：

```sh
bun run benchmark:render
```

## 限制說明

:::caution[引用測試結果前請務必閱讀]
呢個係一項針對**世界生成**嘅專項基準測試，並唔代表 Steel 喺所有伺服器綜合負載下都比原版快 18.8 倍。
:::

- **重複測試嘅區域規模相對適中。**選擇 101×101 區域係為咗令原版 Fabric 亦可以喺合理時間內重複運行三次。301×301 測試展示咗預熱後嘅吞吐量表現，但僅運行咗一次，唔應該將其視為穩定嘅多次平均值。
- **雙方嘅生成階段並非百分百等同。**由於目前大多數實體嘅行為尚未實現，Steel 暫時停用咗區塊生成管線中嘅實體生成（Entity Spawning）階段，而原版 Fabric 執行咗該階段。除此之外，雙方均完整生成咗包含結構與光照嘅完整（`Full`）區塊。
- **Fabric 代表嘅係原版基準線，而非經過深度調優嘅模組服。**Fabric Loader 僅用於載入 Fabric API 與 Chunky，以便自動執行完全一致嘅預生成任務。我哋有意排除咗各類第三方效能優化模組，因為呢啲模組往往需要針對特定負載進行專門調參；若設定不當，反而可能低估佢哋嘅真實實力。我哋非常歡迎熟悉相關優化模組調優嘅開發者提交可重現嘅基準測試對比。
- **測試條件偏向純 CPU 吞吐。**`tmpfs` 記憶體盤、空載伺服器與無玩家連接最大程度排除咗磁碟 I/O 與即時遊戲互動干擾；喺掛載物理硬碟且有玩家在線嘅實際生產環境中，表現會有所唔同。
- **僅反映單一硬件、單一種子碼、單一維度與單一程式碼版本。** 喺得出更廣泛嘅結論之前，仲需要喺更多硬件平台上重現，並將測試擴展到下界、末地、磁碟區塊載入、客戶端區塊發送、遊戲刻（Tick）耗時以及多玩家並行場景。

## 未來基準測試計劃

後續計劃補充嘅測試方向包括：

- 由熟悉相關模組嘅貢獻者提供經過合理調優嘅 Fabric 效能模組設定對比
- 喺更多唔同硬件規格嘅機器上面進行多次重複嘅 301×301 區域生成測試
- 喺物理 NVMe 固態硬碟上面進行測試（包括統計存檔體積與磁碟寫入 Byte 數）
- 下界（The Nether）與末地（The End）維度生成測試
- 已生成區塊嘅磁碟載入效能測試
- 向單一及多個並行客戶端發送區塊嘅網絡吞吐測試
- 模擬多玩家在線時嘅遊戲刻（Tick）耗時與記憶體佔用測試
