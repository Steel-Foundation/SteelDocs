# 程式碼規範

## 一般準則

- **遵循原版命名慣例**：通常原版對各類事物嘅命名相當得體，因此保持相同嘅命名可以令後續閱讀程式碼嘅人更加輕鬆。如果我哋偶爾因為原版名稱唔好、缺乏自解釋性，或者因為我哋採用咗完全唔同嘅解決方案而選擇偏離原版命名，則必須喺相關嘅結構體、方法或模組上方加入詳盡嘅文檔註解（Doc Comment），清晰說明同原版嘅差異，以便後續參與者輕鬆理解你嘅設計。
- **減少程式碼重複**：應盡量避免重複程式碼，但喺必要時重複寥寥數行通常係可以接受嘅。
- **構築穩固基礎，拒絕抄捷徑**：喺開發基礎設施程式碼嗰陣，必須格外確保冇偷工減料或遺漏任何邊界情況，否則日後可能迫使成個底層系統推倒重來。基礎程式碼係指供其他程式碼廣泛依賴嘅系統或介面抽象，例如方塊行為 Trait（Block Behavior Trait）——如果佢一開始設計粗糙，等到上面堆疊咗上百個方塊實現嗰陣，想重構就難過登天喇。然而，只要最初設計嗰陣充分考慮咗長遠演進，呢個並唔排除未來嘅基礎設施改進。我哋區塊調度器（Chunk Scheduler）就係一個良好示範：區塊嘅各個生成階段以及幾時執行嘅規則由一開始就設計完善，呢個意味住未來就算替換調度演算法，亦完全唔會破壞現有嘅生成程式碼。
- **拒絕權宜修補（Workarounds）**：唔好因為某段輔助邏輯喺你目前嘅用例入面只用到一次，就偷懶省去提取獨立輔助函數嘅步驟。
- **避免過深縮進**：善用保護子句（Guard Clauses）提早返回。Rust 提供咗優秀嘅 `if let` 以及 `let Some() = x else { return }` 語法嚟實現扁平化控制流。
- **謹慎觸發 Panic**：除非該分支喺邏輯上絕無可能發生，或者發生咗對成個程式而言屬於無法恢復嘅致命錯誤，否則唔好輕易使用 `panic!`。一般錯誤應當透過 `Result` 向上冒泡。
- **非必要唔使用多線程**：除非你能清晰說明點解某項運算必須多線程化，並用基準測試證明佢確實帶嚟咗效能提升，否則唔好盲目引入多線程。
- **明確非同步（Async）邊界**：除非涉及磁碟或網絡 I/O，或者需要 `await` 大量低運算量嘅調度依賴（例如等待前置區塊依賴，但實際嘅區塊生成運算必須分派至 Rayon 線程池），否則唔好濫用 `async`。切勿喺非同步運行時嘅主工作線程中直接執行 CPU 密集型運算，應透過 `spawn_blocking` 或分派到 Rayon 線程池嚟橋接運算邊界。
- **效能分析工具建議**：推薦使用 [samply](https://github.com/mstange/samply) 或 [jaeger](https://www.jaegertracing.io/docs/latest/getting-started/)。Jaeger 最適合藉助 Tracing Span 進行時序追蹤，捕獲上下文與耗時平均值；若想獲得簡潔直觀嘅火焰圖（Flame Graph）嚟睇世界生成入面究竟邊個內部函數佔用咗最多資源，Samply 就係最佳利器。
- **嚴格控制外部依賴**：我哋唔係 JavaScript 生態，唔需要引入類似 is-even 和 left-pad 呢啲瑣碎依賴。
- **標記未完工特性**：如果某項特性嘅實現尚未完整，請務必喺對應位置留下清晰嘅 `// TODO:` 註解。

## 註冊表規範

- **按需生成，杜絕過度提取**：只有確實需要提取嘅數據先進行生成。例如，原版 Minecraft 對實體喺唔同狀態下嘅碰撞箱變換採用咗寫死計算嗎？如果係，我哋應當直接喺程式碼入面寫死計算，而唔係大費周章提取佢哋。
- **複雜邏輯優先手寫**：除非條目數量極多（30 個以上），否則包含複雜邏輯嘅註冊表應優先手動編寫。例如數據組件（Data Components）與實體序列化器需要大量手動工作嚟確保序列化行為精確無誤，而佢哋嘅條目數量並唔多，完全冇必要再引入一套複雜嘅程式碼生成器嚟徒增困擾。
- **優先複用原版數據包入面嘅數據**：如果某項數據喺 Minecraft 原版數據包（Datapack）入面已存在，應直接使用由數據包提取出嘅原生格式，而唔係另起爐灶生成自訂格式。呢個通常適用於 Mojang 所稱嘅「可重載註冊表」（Reloadable Registries），包括標籤（Tags）、世界生成數據等。原版內置註冊表（BuiltIn Registries）則仍需按需提取。
- **面向未來模組化與 ABI 相容性設計**：由第一日開始就將未來嘅模組支援與 ABI 相容性納入考量。雖然唔強制而家就加入諸如 `Other` 呢啲列舉兜底變體，但程式碼結構必須能夠從容應對未來嘅擴展。喺涉及模組擴展嗰陣，我哋應當看齊 NeoForge 嘅工程標準，就算係方塊註冊表等原版內置註冊表亦應貫徹呢個理念。

## 測試與程式碼審查

- **編寫充分嘅單元測試**：針對複雜嘅高級系統、使用咗 `unsafe` 嘅程式碼（必須嚴格附帶 `// SAFETY:` 註解說明安全不變量），或者需要同原版確定性嚴格對齊嘅程式碼（例如 ItemComponent 雜湊計算或世界生成雜訊），必須編寫單元測試。
- **明確說明 Clippy 規則放寬** ：只有喺附帶清晰說明理由嘅前提下，先允許使用 `#[allow(...)]` 局部放寬 Clippy Lint 規則（顯而易見嘅情況除外）。對於被證實為誤報嘅情況，或為咗提升可讀性而有意偏離規則嘅程式碼（例如函數長度稍長以便完整呈現邏輯流程），只要附帶咗合理嘅解釋註解，都係完全可以接受嘅。
