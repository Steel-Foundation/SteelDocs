Steel 發佈的首份基準測試聚焦於它目前最擅長的工作： **地形生成**。我們將原生編譯的 Steel 伺服器與搭載 [Chunky](https://modrinth.com/plugin/chunky) 預生成外掛的 Fabric 伺服器進行了對比。

:::note[以 Fabric 作為原版基準線]
在本頁所有測試中，**Fabric**均代表安裝了 Fabric Loader、Fabric API 與 Chunky，但**未安裝任何效能最佳化模組**的 Minecraft Java 版 26.2 伺服器。我們將其作為可重複自動執行的原版（Vanilla）對照基準：Chunky 僅負責劃定固定的預生成區域並排程工作，實際的區塊生成完全由 Minecraft 原版世界生成器完成。
:::

在這台測試機器上，三次重複測試中 Steel 生成 10,201 個測試區塊的速度是**Fabric 的 18.8 倍**。

| 伺服器 | 中位數耗時 |     平均吞吐量 | 中位數峰值常駐記憶體 (RSS) | 平均 CPU 使用 |
| ------ | ---------: | -------------: | -------------------------: | ------------: |
| Steel  |     3.95 s | 2,581.8 區塊/s |                   1.79 GiB |     30.2 核心 |
| Fabric |    74.42 s |   137.2 區塊/s |                   2.47 GiB |      4.4 核心 |

耗時與記憶體數據取三次執行的中位數（Median），吞吐量與 CPU 使用量取算術平均數（Mean）。吞吐量越高越好，耗時與記憶體使用量越低越好。

![展示三次冷啟動測試平均區塊生成吞吐量的水平長條圖：Steel 為 2,581.8 區塊/秒，Fabric 為 137.2 區塊/秒。](@/assets/benchmarks/chunk-generation-throughput.svg)

多核心並行擴展能力是這一差距的重要原因：在測量區間內，Steel 平均讓 30.2 個邏輯 CPU 核心保持忙碌運作，而 Fabric 平均僅使用了 4.4 個核心。

![展示平均 CPU 核心使用數的水平長條圖：Steel 為 30.2 核心，Fabric 為 4.4 核心。](@/assets/benchmarks/chunk-generation-cpu.svg)

### 依 CPU 核心時間折算正規化

將吞吐量除以平均 CPU 使用核心數，可以粗略衡量每個 CPU 秒（CPU-second）完成的區塊生成工作量：

| 伺服器 | 每 CPU 秒生成區塊數 | 相對 Fabric 倍率 |
| ------ | ------------------: | ---------------: |
| Steel  |               85.51 |            2.75× |
| Fabric |               31.15 |            1.00× |

經過 CPU 核心數折算後差距有所縮小，但依然顯著：**Steel 每 CPU 秒生成的區塊數約為 Fabric 的 2.75 倍**。當然，單核心效率並不能取代真實牆上時鐘（Wall-clock）吞吐量——閒置的 CPU 核心並不能讓預生成工作提早完成——但這項指標讓我們在觀察多核心並行擴展性之餘，也能直觀看到單核心執行效率的提升。

## 記憶體使用量

在本次測試中，Steel 的峰值常駐記憶體（Peak RSS）同樣較低：其中位數峰值為**1.79 GiB**，而 Fabric 為**2.47 GiB**。

下方折線圖展示了各伺服器中位數耗時那一次執行期間的記憶體變化。曲線提早結束代表該伺服器已經提早完成了所有區塊生成工作，而非記憶體降為零。

![隨時間變化的常駐記憶體（RSS）折線圖：Steel 在約 4.0 秒、1.8 GiB 附近完成生成，而 Fabric 在約 74.4 秒、3.6 GiB 附近完成生成。](@/assets/benchmarks/chunk-generation-memory.svg)

常駐記憶體集大小（RSS）測量的是整個伺服器程序佔用的實體記憶體，而不僅僅是活動區塊資料：對於 Java 而言，這包含了 JVM 本身及已認可的堆積分頁（Committed Heap Pages）；對於 Steel 而言，則包含原生程序與記憶體配置器開銷。該指標反映了作業系統在此負載下實際駐留的記憶體大小，但並不能直接等同於 Java 堆積內活動物件與 Rust 記憶體配置量的對比。

## 更大區域擴展性測試（301×301）

我們還對每個伺服器各執行了一次**301×301 區塊區域**（共**90,601 個區塊**，面積為 101×101 測試的 8.88 倍）的生成測試。更大的區域能讓排程器與執行緒池充分預熱（Warm up），更能體現持續穩定吞吐量；不過單次執行的統計信賴度不及重複三次的 101×101 測試。

| 伺服器 |    耗時 |         吞吐量 | 峰值 RSS | 平均 CPU 使用 | 每 CPU 秒生成區塊數 |
| ------ | ------: | -------------: | -------: | ------------: | ------------------: |
| Steel  | 32.14 s | 2,818.6 區塊/s | 3.98 GiB |     29.4 核心 |               95.86 |
| Fabric | 8:37.39 |   175.1 區塊/s | 3.35 GiB |      4.1 核心 |               42.68 |

在這次大區域執行中，**Steel 的速度是 Fabric 的 16.10 倍**；依平均 CPU 使用核心數折算後，**Steel 每 CPU 秒完成的區塊數是 Fabric 的 2.25 倍**。

在更大區域下，兩個伺服器的平均吞吐量相較各自的 101×101 平均值都有所提升：Steel 提升了 9.2%，Fabric 提升了 27.6%。由於大區域測試在記憶體中保留了更多已生成及待處理的區塊資料，不同區域大小之間的峰值 RSS 不宜直接橫向比較。

![對比 Steel 與 Fabric 在 101×101 三次平均值與 301×301 單次執行下區塊生成吞吐量的分組水平長條圖。](@/assets/benchmarks/chunk-generation-scaling.svg)

## 測試方法論

主基準測試圍繞區塊座標 `(0, 0)` 生成一片全新的**101×101**完整主世界（Overworld）區塊正方形區域，共計**10,201 個目標區塊**（約合 2.61 平方公里）。擴展性測試則使用**301×301**正方形區域，共計**90,601 個目標區塊**（約合 23.19 平方公里）。所有測試均使用以下固定世界種子碼：

```text
8500081009970950196
```

之所以選用這個種子碼，是因為它具有極高密度的生態與地形多樣性：該種子碼的發現者[回報稱在距離原點 (0, 0) 1,000 格範圍內涵蓋了幾乎所有生態域與結構](https://www.reddit.com/r/minecraftseeds/comments/1tf9iz2/ive_been_seedfinding_for_close_to_3_years_now/)，進而能在緊湊的測試區域內廣泛涵蓋各類地形與結構生成邏輯。

雙方的共同測試條件如下：

- Minecraft Java 版 26.2
- 啟用結構（Structures）生成
- 無玩家連線
- 每次執行均使用全新的空白世界目錄
- 世界存檔目錄掛載在同一個 `tmpfs` 記憶體檔案系統上
- 每個伺服器在 101×101 規模下執行三次冷啟動測試，在 301×301 規模下執行一次冷啟動測試
- 每 250 毫秒取樣一次程序 CPU 時間與常駐記憶體（RSS）
- Steel 預生成並行視窗設為 64 區塊（`PREGEN_WINDOW_SIZE=64`）

將世界存檔放在 `tmpfs` 上是為了排除實體磁碟 I/O 瓶頸的干擾——區塊序列化、Zlib 壓縮與檔案寫入呼叫依然照常執行，但實體硬碟讀寫速度不會掩蓋 CPU 生成管線本身的表現。

Steel 的計時起點為日誌輸出 `Preparing spawn area`，終點為 `Spawn area prepared`；Fabric 的計時起點為 Chunky 輸出 `Task started`，終點為 `Task finished`。程序啟動、註冊表載入、出生點選取以及關閉伺服器均不包含在測量計時區間內。

### 如何重現基準測試

基準測試執行器與圖表渲染器均已作為 TypeScript 腳本收錄在本儲存庫中，使用 Bun 執行。在文件儲存庫根目錄下執行：

```sh
PREGEN_WINDOW_SIZE=64 bun run benchmark -- \
  --steel ../SteelMC \
  --fabric ../fabric_server \
  --output /tmp/steel-benchmark \
  --runs 3 --side 101
```

如需執行單次大區域擴展測試，只需將最後一行改為 `--runs 1 --side 301` 並指定另一個輸出目錄。

測試執行器會在每次試驗前建立全新的暫存世界目錄、透過 SHA-512 驗證固定版本的 Chunky 與 Fabric API、取樣 Linux `/proc` 指標，並輸出原始日誌及 JSON / CSV 結果檔案。預設的 `all` 設定會在每次試驗間交替輪換 Steel 與 Fabric 的執行先後順序；也可以使用 `--profile steel` 或 `--profile fabric` 單獨測試其中一個伺服器。

若要根據儲存庫中保存的原始測試資料重新產生 SVG 圖表，可執行：

```sh
bun run benchmark:render
```

## 限制說明

:::caution[引用測試結果前請務必閱讀]
這是一項針對**世界生成**的專項基準測試，並不代表 Steel 在所有伺服器綜合負載下都比原版快 18.8 倍。
:::

- **重複測試的區域規模相對適中。**選擇 101×101 區域是為了讓原版 Fabric 也能在合理時間內重複執行三次。301×301 測試展示了預熱後的吞吐量表現，但僅執行了一次，不應將其視為穩定的多次平均值。
- **雙方的生成階段並非百分之百等同。**由於目前大多數實體的行為尚未實作，Steel 暫時停用了區塊生成管線中的實體生成（Entity Spawning）階段，而原版 Fabric 執行了該階段。除此之外，雙方均完整生成了包含結構與光照的完整（`Full`）區塊。
- **Fabric 代表的是原版基準線，而非經過深度調校的模組伺服器。**Fabric Loader 僅用於載入 Fabric API 與 Chunky，以便自動執行完全一致的預生成工作。我們有意排除了各類第三方效能最佳化模組，因為這些模組往往需要針對特定負載進行專門調校；若設定不當，反而可能低估它們的真實實力。我們非常歡迎熟悉相關最佳化模組調校的開發者提交可重現的基準測試對比。
- **測試條件偏向純 CPU 運算。**`tmpfs` 記憶體磁碟、閒置伺服器與無玩家連線最大程度排除了磁碟 I/O 與即時遊戲互動干擾；在掛載實體硬碟且有玩家在線的實際正式環境中，表現會有所不同。
- **僅反映單一硬體、單一種子碼、單一維度與單一程式碼版本。** 在得出更廣泛的結論之前，還需要在更多硬體平台上重現，並將測試擴展到地獄、終界、磁碟區塊載入、用戶端區塊傳送、遊戲刻（Tick）耗時以及多玩家並行情境。

## 未來基準測試計畫

後續計畫補充的測試方向包括：

- 由熟悉相關模組的貢獻者提供經過合理調校的 Fabric 效能模組設定對比
- 在更多不同硬體規格的機器上進行多次重複的 301×301 區域生成測試
- 在實體 NVMe 固態硬碟上進行測試（包括統計存檔大小與磁碟寫入位元組數）
- 地獄（The Nether）與終界（The End）維度生成測試
- 已生成區塊的磁碟載入效能測試
- 向單一及多個並行用戶端傳送區塊的網路吞吐測試
- 模擬多玩家在線時的遊戲刻（Tick）耗時與記憶體使用量測試
