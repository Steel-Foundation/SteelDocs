# 程式碼規範

## 一般準則

- **遵循原版命名慣例**：通常原版對各類事物的命名相當妥當，因此維持相同的命名可以讓後續閱讀程式碼的人更加輕鬆。如果我們偶爾因為原版名稱不佳、缺乏自解釋性，或者因為我們採用了完全不同的解決方案而選擇偏離原版命名，則必須在相關的結構體、方法或模組上方加入詳盡的文件註解（Doc Comment），清楚說明與原版的差異，以便後續參與者輕鬆理解你的設計。
- **減少程式碼重複**：應盡量避免重複程式碼，但在必要時重複寥寥數行通常是可以接受的。
- **構築穩固基礎，拒絕抄捷徑**：在開發基礎設施程式碼時，必須格外確保沒有偷工減料或遺漏任何邊界情況，否則日後可能迫使整個底層系統打掉重練。基礎程式碼是指供其他程式碼廣泛依賴的系統或介面抽象，例如方塊行為 Trait（Block Behavior Trait）——如果它一開始設計粗糙，等到上面堆疊了上百個方塊實作時，想重構就難如登天了。然而，只要最初設計時充分考慮了長遠演進，這並不排斥未來的基礎設施改進。我們區塊排程器（Chunk Scheduler）就是一個良好示範：區塊的各個生成階段以及何時執行的規則從一開始就設計完善，這意味著未來即便替換排程演算法，也完全不會破壞現有的生成程式碼。
- **拒絕權宜修補（Workarounds）**：不要因為某段輔助邏輯在你目前的使用案例中只用到一次，就偷懶省去提取獨立輔助函式的步驟。
- **避免過深巢狀縮排**：善用保護子句（Guard Clauses）提早返回。Rust 提供了優異的 `if let` 以及 `let Some() = x else { return }` 語法來實現扁平化控制流程。
- **謹慎觸發 Panic**：除非該分支在邏輯上絕無可能發生，或者發生了對整個程式而言屬於無法復原的致命錯誤，否則不要輕易使用 `panic!`。一般錯誤應當透過 `Result` 向上傳遞。
- **非必要不使用多執行緒**：除非你能清楚說明為什麼某項運算必須多執行緒化，並用基準測試證明其確實帶來了效能提升，否則不要盲目引進多執行緒。
- **明確非同步（Async）邊界**：除非涉及磁碟或網路 I/O，或者需要 `await` 大量低運算量的排程相依性（例如等待前置區塊相依性，但實際的區塊生成運算必須分派至 Rayon 執行緒池），否則不要濫用 `async`。切勿在非同步執行期的主工作執行緒中直接執行 CPU 密集型運算，應透過 `spawn_blocking` 或分派至 Rayon 執行緒池來橋接運算邊界。
- **效能分析工具建議**：推薦使用 [samply](https://github.com/mstange/samply) 或 [jaeger](https://www.jaegertracing.io/docs/latest/getting-started/)。Jaeger 最適合藉由 Tracing Span 進行時序追蹤，擷取情境與耗時平均值；若想獲得簡潔直觀的火焰圖（Flame Graph）來查看世界生成中究竟哪個內部函式佔用了最多資源，Samply 則是最佳工具。
- **嚴格控制外部依賴**：我們不是 JavaScript 生態，不需要引入類似 is-even 和 left-pad 這樣的零碎依賴。
- **標記未完工特性**：如果某項特性的實作尚未完整，請務必在對應位置留下清晰的 `// TODO:` 註解。

## 註冊表規範

- **依需求生成，杜絕過度提取**：只有確實需要提取的資料才進行生成。例如，原版 Minecraft 對實體在不同狀態下的碰撞箱變換採用了寫死計算嗎？如果是，我們應當直接在程式碼中寫死計算，而非大費周章提取它們。
- **複雜邏輯優先手寫**：除非項目數量極多（30 個以上），否則包含複雜邏輯的註冊表應優先手動撰寫。例如資料元件（Data Components）與實體序列化器需要大量手動工作來確保序列化行為精確無誤，而它們的項目數量並不多，完全沒有必要再引入一套複雜的程式碼產生器來徒增困擾。
- **優先複用原版資料包中的資料**：如果某項資料在 Minecraft 原版資料包（Datapack）中已存在，應直接使用從資料包中提取出的原生格式，而不是另起爐灶生成自訂格式。這通常適用於 Mojang 所稱的「可重載註冊表」（Reloadable Registries），包括標籤（Tags）、世界生成資料等。原版內建註冊表（BuiltIn Registries）則仍需依需求提取。
- **面向未來模組化與 ABI 相容性設計**：從第一天起就將未來的模組支援與 ABI 相容性納入考量。雖然不強制現在就加入諸如 `Other` 這樣的列舉兜底變體，但程式碼結構必須能夠從容應對未來的擴充。在涉及模組擴充時，我們應當看齊 NeoForge 的工程標準，即便是方塊註冊表等原版內建註冊表也應貫徹這一理念。

## 測試與程式碼審查

- **撰寫充分的單元測試**：針對複雜的高階系統、使用了 `unsafe` 的程式碼（必須嚴格附帶 `// SAFETY:` 註解說明安全不變量），或者需要與原版確定性嚴格對齊的程式碼（例如 ItemComponent 雜湊計算或世界生成雜訊），必須撰寫單元測試。
- **明確說明 Clippy 規則放寬** ：只有在附帶清晰說明理由的前提下，才允許使用 `#[allow(...)]` 局部放寬 Clippy Lint 規則（顯而易見的情況除外）。對於被證實為誤報的情況，或為了提升可讀性而有意偏離規則的程式碼（例如函式長度稍長以便完整呈現邏輯流程），只要附帶了合理的解釋註解，都是完全可以接受的。
