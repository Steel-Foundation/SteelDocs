在本指南中，你將了解到開始為 SteelMC 貢獻程式碼所需掌握的全部必要知識與流程規範。

:::note
本指南假設你已經掌握了 Git 和 GitHub 的基本操作與協作流程。
:::

:::tip
身為新貢獻者，請盡量將同時開啟的 Pull Request（PR）數量控制在 3 個以內，以便維護者團隊在開啟新 PR 之前先對現有 PR 提供即時的程式碼審查回饋。
此外，建議先從較小、較簡單的貢獻開始（單次變更量大約在 1,000 行以內），這樣審查與合併的速度會快得多。

維護者通常是在閒暇時間審查 PR，因此初次審查可能需要幾天時間。如果一週後仍未收到回饋，歡迎在 Discord 中交流或在你的 PR 下方留言提醒我們。
:::

## 開始之前

在正式動手寫程式碼前，你需要先了解 Steel 設計哲學中的幾項核心理念。

### 程式碼哲學

為 Steel 撰寫程式碼時請牢記：我們需要的是 **完整且成熟的解決方案，而非半成品的權宜之計**。對於中大型系統，必須先深入研究該機制在原版 Minecraft 中的運作方式，並思考如何將其設計得更合理、更高效。我們在建構時始終注重打下穩固的工程基礎，這意味著所有程式碼必須具備高可讀性、詳盡的程式碼文件（Doc Comments）、良好的凝聚性，並達到正式環境等級標準。如果你負責的系統在未來可能需要支援模組擴充，請從一開始就為未來的擴充性預留空間。

### AI 輔助政策

我們不限制你使用 AI 工具的方式，前提是你必須確保自己**完全理解 PR 中的每一行程式碼**，能夠清楚解釋開發過程中的所有架構決策，並能說明在提交 PR 之前你評估過哪些替代方案、為何沒有採用它們。

### 程式碼規範

在開始前，請務必閱讀[我們的程式碼規範](../code-standard)。

## 開發準備

了解了我們的設計哲學後，就可以開始著手開發了，不過在此之前……

### 選擇要做什麼

尋找切入點的方法有很多，我們推薦依以下步驟進行：

- 查看[已開啟的 PR](https://github.com/Steel-Foundation/SteelMC/pulls)，了解其他人正在開發哪些內容，避免重複投入
- 查看[未解決的 Issue](https://github.com/Steel-Foundation/SteelMC/issues)，挑選可修復的問題（推薦依 `good first issue` 標籤進行篩選）
- 查看[實作進度追蹤器](../../tracker)，查看哪些方塊、物品、實體或指令尚未實作
- 在[我們的 Discord 社群](/discord)的 `#dev-work` 頻道中交流確認，確認你計畫實作的功能是否適合目前階段

### 建立新分支

首先，如果你的 GitHub 帳號下還沒有 SteelMC 的 Fork 複本，請前往 [Fork 頁面建立](https://github.com/Steel-Foundation/SteelMC/fork)。

在你的 Fork 儲存庫中，建立一個新分支，並在分支名稱中明確指出你正在實作的功能。

:::caution
除非你非常清楚自己在做什麼，否則請務必基於我們的 `main` 或 `dev` 主幹分支建立新分支，切勿基於某個正在開發中的功能分支切出。
:::

將該分支複製（Clone）到本機開發裝置即可開始撰寫程式碼。

## 開發完成後的檢查

當你完成功能實作、通過充分的自我測試、確保本機分支已同步至最新提交並推送至 GitHub 遠端分支後，就可以向官方儲存庫發起 Pull Request 了。但在提交前，請先確保你的程式碼已通過各項品質檢查。

:::note
程式碼庫中設定了自動化品質檢查，可執行以下指令檢查程式碼規範：

```bash
# 執行靜態程式碼分析（Clippy）
cargo clippy -r --all-targets --all-features

# 檢查程式碼格式是否符合規範
cargo fmt --all --check

# 檢查程式碼中的錯別字
typos
```

關於如何安裝 `typos` 工具，請參考[此處安裝說明](https://crates.io/crates/typos-cli#install)。

程式碼庫中內建了 [Prek](https://prek.j178.dev/) 設定檔，你可以直接在本機執行 `prek` 自動執行完整的審查前檢查：

```bash
prek run
```
:::

提交 PR 時，請依官方範本清楚填寫 PR 標題與說明描述。

此外，你可以在 GitHub 上直接請求維護者審查，或將 PR 連結發送到 Discord 的 `prs-ready-for-review` 頻道，方便維護者即時跟進。

維護者可能會向你提出修改請求（Request Changes）。如果遇到這種情況，請根據意見修改程式碼，或者說明你認為目前做法更好的理由。

最終，你的程式碼將被合併進主幹分支。當那一刻來臨，請記住：\**「感謝並祝賀你為 SteelMC 貢獻的程式碼！」**
