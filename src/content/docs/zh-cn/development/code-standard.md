# 代码规范

## 通用准则

- **遵循原版命名惯例**：通常原版对各类事物的命名相当体面，因此保持相同的命名可以让后续阅读代码的人更加轻松。如果我们偶尔因为原版名称不佳、缺乏自解释性，或者因为我们采用了完全不同的解决方案而选择偏离原版命名，则必须在相关的结构体、方法或模块上方添加详尽的文档注释（Doc Comment），清晰说明与原版的差异，以便后续参与者轻松理解你的设计。
- **减少代码重复**：应尽量避免重复代码，但在必要时重复寥寥数行通常是可以接受的。
- **构筑稳固基底，拒绝抄近道**：在开发基础设施代码时，必须格外确保没有偷工减料或遗漏任何边界情况，否则日后可能迫使整个底层系统推倒重来。基础代码是指供其他代码广泛依赖的系统或接口抽象，例如方块行为 Trait（Block Behavior Trait）——如果它一开始设计粗糙，等到上面堆叠了上百个方块实现时，想重构就难如登天了。然而，只要最初设计时充分考虑了长久演进，这并不排斥未来的基础设施改进。我们区块调度器（Chunk Scheduler）就是一个良好示范：区块的各个生成阶段以及何时执行的规则从一开始就设计完备，这意味着未来即便替换调度算法，也完全不会破坏现有的生成代码。
- **拒绝权宜修补（Workarounds）**：不要因为某段辅助逻辑在你当前的用例中只用到一次，就偷懒省去提取独立辅助函数的步骤。
- **避免过深嵌套**：善用保护子句（Guard Clauses）尽早返回。Rust 提供了优秀的 `if let` 以及 `let Some() = x else { return }` 语法来实现扁平化控制流。
- **谨慎触发 Panic**：除非该分支在逻辑上绝无可能发生，或者发生了对整个程序而言属于无法恢复的致命故障，否则不要轻易使用 `panic!`。常规错误应当通过 `Result` 向上冒泡。
- **非必要不使用多线程**：除非你能清晰阐明为什么某项计算必须多线程化，并用基准测试证明其确实带来了性能提升，否则不要盲目引入多线程。
- **明确异步（Async）边界**：除非涉及磁盘或网络 I/O，或者需要 `await` 大量低计算量的调度依赖（例如等待前置区块依赖，但实际的区块生成计算必须派发到 Rayon 线程池），否则不要滥用 `async`。切勿在异步运行时的主工作线程中直接执行 CPU 密集型计算，应通过 `spawn_blocking` 或派发到 Rayon 线程池来弥合计算边界。
- **性能分析工具建议**：推荐使用 [samply](https://github.com/mstange/samply) 或 [jaeger](https://www.jaegertracing.io/docs/latest/getting-started/)。Jaeger 最适合借助 Tracing Span 进行时序追踪，捕获上下文与耗时均值；若想获得简洁直观的火焰图（Flame Graph）来查看世界生成中究竟哪个内部函数占用了最多资源，Samply 则是最佳利器。
- **严控外部依赖**：我们不是 JavaScript 生态，不需要引入类似 is-even 和 left-pad 这样的琐碎依赖。
- **标记未完工特性**：如果某项特性的实现尚未完整，请务必在对应位置留下清晰的 `// TODO:` 注释。

## 注册表规范

- **按需生成，杜绝过度提取**：只有确实需要提取的数据才进行生成。例如，原版 Minecraft 对实体在不同状态下的碰撞箱变换采用了硬编码计算吗？如果是，我们应当直接在代码中硬编码计算，而非大费周章提取它们。
- **复杂逻辑优先手写**：除非条目数量极多（30 个以上），否则包含复杂逻辑的注册表应优先手动编写。例如数据组件（Data Components）与实体序列化器需要大量手动工作来确保序列化行为精确无误，而它们的条目数量并不多，完全没有必要再引入一套复杂的代码生成器来徒增烦恼。
- **优先复用原版数据包中的数据**：如果某项数据在 Minecraft 原版数据包（Datapack）中已存在，应直接使用从数据包中提取出的原生格式，而不是另起炉灶生成自定义格式。这通常适用于 Mojang 所称的“可重载注册表”（Reloadable Registries），包括标签（Tags）、世界生成数据等。原版内置注册表（BuiltIn Registries）则仍需按需提取。
- **面向未来模组化与 ABI 兼容性设计**：从第一天起就将未来的模组支持与 ABI 兼容性纳入考量。虽然不强制现在就添加诸如 `Other` 这样的枚举兜底变体，但代码结构必须能够从容应对未来的扩展。在涉及模组扩展时，我们应当看齐 NeoForge 的工程标准，即便是方块注册表等原版内置注册表也应贯彻这一理念。

## 测试与代码审查

- **编写充分的单元测试**：针对复杂的高级系统、使用了 `unsafe` 的代码（必须严格附带 `// SAFETY:` 注释说明安全不变量），或者需要与原版确定性严格对齐的代码（例如 ItemComponent 哈希计算或世界生成噪声），必须编写单元测试。
- **显式说明 Clippy 规则放宽** ：只有在附带清晰说明理由的前提下，才允许使用 `#[allow(...)]` 局部放宽 Clippy Lint 规则（显而易见的情况除外）。对于被证实为误报的情况，或为了提升可读性而有意偏离规则的代码（例如函数长度稍长以便完整呈现逻辑流程），只要附带了合理的解释注释，都是完全可以接受的。
