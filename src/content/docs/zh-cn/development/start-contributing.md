在本指南中，你将了解到开始为 SteelMC 贡献代码所需掌握的全部必要知识与流程规范。

:::note
本指南假定你已经掌握了 Git 和 GitHub 的基础操作与协作流程。
:::

:::tip
作为新贡献者，请尽量将同时开启的 Pull Request（PR）数量控制在 3 个以内，以便维护者团队在开启新 PR 之前先对现有 PR 提供及时的代码审查反馈。
此外，建议先从较小、较清晰的代码贡献开始（单次修改量大约在 1,000 行以内），这样审查与合并周期会快得多。

维护者通常是在业余时间审查 PR，因此初次审查可能需要几天时间。如果一周后仍未收到反馈，欢迎在 Discord 中交流或在你的 PR 下留言提醒我们。
:::

## 开始之前

在正式动笔写代码前，你需要先了解 Steel 设计哲学中的几项核心理念。

### 代码哲学

为 Steel 编写代码时请牢记：我们需要的是 **完整且成熟的解决方案，而非半成品的权宜之计**。对于中大型系统，必须先深入调研该机制在原版 Minecraft 中的工作方式，并思考如何将其设计得更合理、更高效。我们在构建时始终注重打下良好的工程基底，这意味着所有代码必须具备高可读性、详尽的代码文档（Doc Comments）、良好的内聚性，并达到生产级标准。如果你负责的系统在未来可能需要对模组扩展开放，请从一开始就为未来的扩展性预留空间。

### AI 辅助政策

我们不限制你使用 AI 工具的方式，前提是你必须确保自己**完全理解 PR 中的每一行代码**，能够清晰解释开发过程中的所有架构决策，并能说明在提交 PR 之前你评估过哪些替代方案、为何没有采用它们。

### 代码规范

在开始前，请务必阅读[我们的代码规范](../code-standard)。

## 开发准备

了解了我们的设计哲学后，就可以开始着手开发了，不过在此之前……

### 选择要做什么

寻找切入点的方法有很多，我们推荐按以下步骤进行：

- 查看[已开启的 PR](https://github.com/Steel-Foundation/SteelMC/pulls)，了解其他人正在开发哪些内容，避免重复劳动
- 查看[未解决的 Issue](https://github.com/Steel-Foundation/SteelMC/issues)，挑选可修复的问题（推荐按 `good first issue` 标签进行筛选）
- 查看[特性实现追踪器](../../tracker)，查看哪些方块、物品、实体或命令尚未实现
- 在[我们的 Discord 社区](/discord)的 `#dev-work` 频道中交流确认，确认你计划实现的特性是否适合当前阶段

### 创建新分支

首先，如果你的 GitHub 账号下还没有 SteelMC 的 Fork 副本，请前往 [Fork 页面创建](https://github.com/Steel-Foundation/SteelMC/fork)。

在你的 Fork 仓库中，新建一个分支，并在分支名称中明确体现你正在实现的功能。

:::caution
除非你非常清楚自己在做什么，否则请务必基于我们的 `main` 或 `dev` 主干分支创建新分支，切勿基于某个正在开发中的功能分支切出。
:::

将该分支克隆（Clone）到本地开发设备即可开始编写代码。

## 开发完成后的检查

当你完成功能实现、通过充分的自我测试、确保本地分支已同步至最新提交并推送到 GitHub 远程分支后，就可以向官方仓库发起 Pull Request 了。但在提交前，请先确保你的代码已通过各项质量检查。

:::note
代码库中配置了自动化质量检查，可运行以下命令检查代码规范：

```bash
# 运行静态代码检查（Clippy）
cargo clippy -r --all-targets --all-features

# 检查代码格式是否规范
cargo fmt --all --check

# 检查代码中的拼写错误
typos
```

关于如何安装 `typos` 工具，请参考[此处安装说明](https://crates.io/crates/typos-cli#install)。

代码库中内置了 [Prek](https://prek.j178.dev/) 配置文件，你可以直接在本地运行 `prek` 自动执行完整的代码审查前检查：

```bash
prek run
```
:::

提交 PR 时，请按官方模板清晰填写 PR 标题与描述说明。

此外，你可以在 GitHub 上直接请求维护者审查，或将 PR 链接发送到 Discord 的 `prs-ready-for-review` 频道，方便维护者及时跟进。

维护者可能会向你提出修改建议（Request Changes）。如果遇到这种情况，请根据意见修改代码，或者说明你认为当前方案更优的理由。

最终，你的代码将被合并进主干分支。当那一刻来临，请记住：\**“感谢并祝贺你为 SteelMC 贡献的代码！”**
