Steel 发布的首份基准测试聚焦于它目前最擅长的任务： **地形生成**。我们将原生编译的 Steel 服务端与搭载 [Chunky](https://modrinth.com/plugin/chunky) 预生成插件的 Fabric 服务端进行了对比。

:::note[以 Fabric 作为原版基线]
在本页所有测试中，**Fabric**均代表安装了 Fabric Loader、Fabric API 与 Chunky，但**未安装任何性能优化模组**的 Minecraft Java 版 26.2 服务端。我们将其作为可重复自动执行的原版（Vanilla）对照基线：Chunky 仅负责划定固定的预生成区域并调度任务，实际的区块生成完全由 Minecraft 原版世界生成器完成。
:::

在这台测试机上，三次重复测试中 Steel 生成 10,201 个测试区块的速度是**Fabric 的 18.8 倍**。

| 服务端 | 中位耗时 |     平均吞吐量 | 中位峰值常驻内存 (RSS) | 平均 CPU 占用 |
| ------ | -------: | -------------: | ---------------------: | ------------: |
| Steel  |   3.95 s | 2,581.8 区块/s |               1.79 GiB |     30.2 核心 |
| Fabric |  74.42 s |   137.2 区块/s |               2.47 GiB |      4.4 核心 |

耗时与内存数据取三次运行的中位数（Median），吞吐量与 CPU 占用取算术平均值（Mean）。吞吐量越高越好，耗时与内存占用越低越好。

![展示三次冷启动测试平均区块生成吞吐量的水平柱状图：Steel 为 2,581.8 区块/秒，Fabric 为 137.2 区块/秒。](@/assets/benchmarks/chunk-generation-throughput.svg)

多核并行扩展能力是这一差距的重要原因：在测量区间内，Steel 平均使 30.2 个逻辑 CPU 核心保持满载工作，而 Fabric 平均仅占用了 4.4 个核心。

![展示平均 CPU 核心占用数的水平柱状图：Steel 为 30.2 核心，Fabric 为 4.4 核心。](@/assets/benchmarks/chunk-generation-cpu.svg)

### 按 CPU 核心时间折算归一化

将吞吐量除以平均 CPU 占用核数，可以粗略衡量每个 CPU 秒（CPU-second）完成的区块生成工作量：

| 服务端 | 每 CPU 秒生成区块数 | 相对 Fabric 倍率 |
| ------ | ------------------: | ---------------: |
| Steel  |               85.51 |            2.75× |
| Fabric |               31.15 |            1.00× |

经过 CPU 核数折算后差距有所收窄，但依然显著：**Steel 每 CPU 秒生成的区块数约为 Fabric 的 2.75 倍**。当然，单核效率并不能替代真实墙钟时间（Wall-clock）吞吐量——闲置围观的 CPU 核心并不能让预生成任务提前跑完——但这一指标让我们在观察多核并行扩展性之余，也能直观看到单核执行效率的提升。

## 内存占用

在本次测试中，Steel 的峰值常驻内存（Peak RSS）同样更低：其中位峰值内存为**1.79 GiB**，而 Fabric 为**2.47 GiB**。

下方折线图展示了各服务端中位耗时那一次运行期间的内存变化。曲线提前结束代表该服务端已经提前完成了全部区块生成任务，而非内存跌落归零。

![随时间变化的常驻内存（RSS）折线图：Steel 在约 4.0 秒、1.8 GiB 附近完成生成，而 Fabric 在约 74.4 秒、3.6 GiB 附近完成生成。](@/assets/benchmarks/chunk-generation-memory.svg)

常驻内存集大小（RSS）测量的是整个服务端进程占用的物理内存，而不仅仅是活动区块数据：对于 Java 而言，这包含了 JVM 自身及已提交的堆内存页（Committed Heap Pages）；对于 Steel 而言，则包含原生进程与内存分配器开销。该指标反映了操作系统在此负载下实际驻留的内存大小，但并不能直接等同于 Java 堆内活动对象与 Rust 堆分配量的对比。

## 更大区域扩展性测试（301×301）

我们还对每个服务端各运行了一次**301×301 区块区域**（共**90,601 个区块**，面积为 101×101 测试的 8.88 倍）的生成测试。更大的区域能让调度器与线程池充分预热（Warm up），更能体现持续稳定吞吐量；不过单次运行的统计置信度不及重复三次的 101×101 测试。

| 服务端 |    耗时 |         吞吐量 | 峰值 RSS | 平均 CPU 占用 | 每 CPU 秒生成区块数 |
| ------ | ------: | -------------: | -------: | ------------: | ------------------: |
| Steel  | 32.14 s | 2,818.6 区块/s | 3.98 GiB |     29.4 核心 |               95.86 |
| Fabric | 8:37.39 |   175.1 区块/s | 3.35 GiB |      4.1 核心 |               42.68 |

在这次大区域运行中，**Steel 的速度是 Fabric 的 16.10 倍**；按平均 CPU 占用核数折算后，**Steel 每 CPU 秒完成的区块数是 Fabric 的 2.25 倍**。

在更大区域下，两个服务端的平均吞吐量相较各自的 101×101 均值都有所提升：Steel 提升了 9.2%，Fabric 提升了 27.6%。由于大区域测试在内存中保留了更多已生成及待处理的区块数据，不同区域尺寸之间的峰值 RSS 不宜直接横向比较。

![对比 Steel 与 Fabric 在 101×101 三次均值与 301×301 单次运行下区块生成吞吐量的分组水平柱状图。](@/assets/benchmarks/chunk-generation-scaling.svg)

## 测试方法论

主基准测试围绕区块坐标 `(0, 0)` 生成一片全新的**101×101**完整主世界（Overworld）区块正方形区域，共计**10,201 个目标区块**（约合 2.61 平方公里）。扩展性测试则使用**301×301**正方形区域，共计**90,601 个目标区块**（约合 23.19 平方公里）。所有测试均使用以下固定世界种子：

```text
8500081009970950196
```

之所以选用这个种子，是因为它具有极高密度的生态与地形多样性：该种子的发现者[报告称在距离原点 (0, 0) 1,000 格范围内涵盖了几乎所有生物群系与结构](https://www.reddit.com/r/minecraftseeds/comments/1tf9iz2/ive_been_seedfinding_for_close_to_3_years_now/)，从而能在紧凑的测试区域内广泛覆盖各类地形与结构生成逻辑。

双方的公共测试条件如下：

- Minecraft Java 版 26.2
- 启用结构（Structures）生成
- 无玩家连接
- 每次运行均使用全新的空白世界目录
- 世界存档目录挂载在同一个 `tmpfs` 内存文件系统上
- 每个服务端在 101×101 规模下执行三次冷启动运行，在 301×301 规模下执行一次冷启动运行
- 每 250 毫秒采样一次进程 CPU 时间与常驻内存（RSS）
- Steel 预生成并发窗口设为 64 区块（`PREGEN_WINDOW_SIZE=64`）

将世界存档放在 `tmpfs` 上是为了剔除物理磁盘 I/O 瓶颈的干扰——区块序列化、Zlib 压缩与文件写入调用依然照常执行，但物理硬盘读写速度不会掩盖 CPU 生成管线本身的表现。

Steel 的计时起点为日志输出 `Preparing spawn area`，终点为 `Spawn area prepared`；Fabric 的计时起点为 Chunky 输出 `Task started`，终点为 `Task finished`。进程启动、注册表加载、出生点选取以及关服退出均不包含在测量计时区间内。

### 如何复现基准测试

基准测试驱动脚本与图表渲染器均已作为 TypeScript 脚本收录在本仓库中，使用 Bun 运行。在文档仓库根目录下执行：

```sh
PREGEN_WINDOW_SIZE=64 bun run benchmark -- \
  --steel ../SteelMC \
  --fabric ../fabric_server \
  --output /tmp/steel-benchmark \
  --runs 3 --side 101
```

如需运行单次大区域扩展测试，只需将最后一行改为 `--runs 1 --side 301` 并指定另一个输出目录。

测试运行器会在每次试验前创建全新的临时世界目录、通过 SHA-512 校验固定版本的 Chunky 与 Fabric API、采集 Linux `/proc` 指标，并输出原始日志及 JSON / CSV 结果文件。默认的 `all` 配置会在每次试验间交替轮换 Steel 与 Fabric 的执行先后顺序；也可以使用 `--profile steel` 或 `--profile fabric` 单独测试其中一个服务端。

若要根据仓库中保存的原始测试数据重新渲染 SVG 图表，可运行：

```sh
bun run benchmark:render
```

## 局限性说明

:::caution[引用测试结果前请务必阅读]
这是一项针对**世界生成**的专项基准测试，并不代表 Steel 在所有服务端综合负载下都比原版快 18.8 倍。
:::

- **重复测试的区域规模相对适中。**选择 101×101 区域是为了让原版 Fabric 也能在合理时间内重复运行三次。301×301 测试展示了预热后的吞吐量表现，但仅运行了一次，不应将其视为稳定的多次平均值。
- **双方的生成阶段并非百分之百等同。**由于目前大多数实体的行为尚未实现，Steel 暂时禁用了区块生成管线中的实体生成（Entity Spawning）阶段，而原版 Fabric 执行了该阶段。除此之外，双方均完整生成了包含结构与光照的完整（`Full`）区块。
- **Fabric 代表的是原版基线，而非经过深度调优的模组服。**Fabric Loader 仅用于加载 Fabric API 与 Chunky，以便自动执行完全一致的预生成任务。我们有意排除了各类第三方性能优化模组，因为这些模组往往需要针对特定负载进行专门调参；若配置不当，反而可能低估它们的真实实力。我们非常欢迎熟悉相关优化模组调优的开发者提交可复现的基准测试对比。
- **测试条件偏向纯 CPU 吞吐。**`tmpfs` 内存盘、空载服务器与无玩家连接最大程度排除了磁盘 I/O 与实时游戏交互干扰；在挂载物理硬盘且有玩家在线的实际生产环境中，表现会有所不同。
- **仅反映单一硬件、单一立种、单一维度与单一代码版本。** 在得出更广泛的结论之前，还需要在更多硬件平台上复现，并将测试扩展到下界、末地、磁盘区块加载、客户端区块发送、游戏刻（Tick）耗时以及多玩家并发场景。

## 未来基准测试计划

后续计划补充的测试方向包括：

- 由熟悉相关模组的贡献者提供经过合理调优的 Fabric 性能模组配置对比
- 在更多不同硬件规格的机器上进行多次重复的 301×301 区域生成测试
- 在物理 NVMe 固态硬盘上进行测试（包括统计存档体积与磁盘写入字节数）
- 下界（The Nether）与末地（The End）维度生成测试
- 已生成区块的磁盘加载性能测试
- 向单个及多个并发客户端发送区块的网络吞吐测试
- 模拟多玩家在线时的游戏刻（Tick）耗时与内存占用测试
