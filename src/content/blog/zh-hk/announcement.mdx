SteelMC 係一個用 Rust 編寫嘅「全新」Minecraft 伺服器。唔使去更新 [*距離上一個 Rust Minecraft 伺服器誕生已經過咗幾多日*](https://dayssincelastrustmcserver.com/) 喇——早喺 2025 年 10 月 16 日，我哋就已經被收錄喺上面。

我一直唔鍾意喺代碼倉庫剛建立嘅嗰一刻就大鑼大鼓咁官宣項目。因為大家嘅反應通常都係「幾型喎，等佢真係行得起再叫我」。而等到項目真係做出啲成績嗰陣，佢一係已經半途夭折，一係早就俾大家遺忘咗。

所以我選擇咗等待。

Steel 喺 2026 年 5 月 20 日首次實現咗逐方塊（Block-for-block）嘅原版地形生成相容。目前嘅相容性測試套件覆蓋咗 7,500 個隨機抽取嘅區塊：主世界、下界與末地三個維度各 2,500 個。

Steel 目前仍處於 Pre-Alpha 階段，但你而家已經可以連接進入伺服器、探索持久化生成嘅世界、與方塊同物品欄互動，並喺現有基礎之上開始建造。

過去呢九個月嘅大部分精力，都投入咗去玩家入服時幾乎察覺唔到嘅底層系統入面。隨住呢啲底層基建走向成熟，後續新增遊戲玩法所需嘅配套支撐會越嚟越少，越嚟越多嘅工作成果將會直觀咁體現喺遊戲體驗入面。

## 簡而言之：Steel 今日做到啲咩

Steel 嘅目標係緊貼 Minecraft Java 版最新正式版，目前適配版本為 **26.2**。客戶端可以加入伺服器、載入生成嘅世界、移動與互動、使用物品欄與指令，並喺之後重新返到已保存嘅世界。呢啲系統係喺一個持久化嘅多人聯機伺服器入面協同運作，而唔單止係孤立嘅網絡協議或者世界生成演示。

生存模式玩法目前尚未完善，只有少數幾種實體類型實現咗完整嘅行為邏輯，而且 Steel 尚未達到完全嘅原版特性相容或協議相容。插件（Plugin）系統亦暫未推出，為 Paper、Bukkit、Fabric、Forge 或 NeoForge 編寫嘅擴展均無法直接使用。我絕唔會誇下海口叫你聽日就將生產環境入面嘅 Paper 伺服器換成 Steel。

## 我點解要發起 Steel

喺開始寫 Steel 之前，我曾長期為 [PumpkinMC](https://github.com/Pumpkin-MC/Pumpkin) 貢獻程式碼。Pumpkin 係我開始用 Rust 編寫 Minecraft 伺服器嘅契機，下文提到嘅任何內容都絕非對 Pumpkin 貢獻者們嘅批評。呢啲記述基於 2025 年 10 月前後嘅 Pumpkin 程式碼庫，如今佢可能已經有咗好大變化。

我熱愛 Rust 嘅一點在於，隨住你對呢門語言理解加深，佢嘅種種限制會變得越嚟越合情合理。一個令人頭痕嘅編譯器報錯，往往係保護緊你避開某個未曾考慮過嘅邊界情況。呢種「有人已經將問題深思熟慮過」嘅感覺，開始塑造我對自己所建構系統嘅期望。

我喺嗰度實現咗紅石系統，並重寫咗物品欄系統。喺貢獻程式碼嘅過程中，我逐漸意識到自己喺對待底層基礎系統時有住唔同嘅取向：我希望先退後一步，研究清楚後續會遇到嘅複雜場景，確保底層架構唔單止應付到眼前嘅第一個用例，仲能夠支撐起未來嘅演進。

當 Pumpkin 開始為世界生成器加入樹木時，呢種理念差異變得尤為明顯。當時每個區塊都係孤立生成嘅——呢個做法喺大多數時候都冇問題，但一旦靠近區塊邊界嘅樹需要將樹葉放置到相鄰區塊入面，問題就嚟喇。我花咗大約一個月研究呢個問題，並逐漸意識到佢嘅本質係點樣協調一整個區域嘅生成流程，而唔單單係放一棵樹。項目最終合併咗另一個能解決燃眉之急嘅方案。兩種優先級都冇錯，但嗰件事令我明確意識到，我想圍繞另一種理念去建構伺服器。

於是我啟動咗 Steel，起初並冇抱太高預期。我動手實現嘅第一件事，就係參與 Pumpkin 時一直心心念念嘅方塊註冊表（Block Registry）與方塊屬性（Property）系統。呢次係我第一次能夠深入研究原版係點樣處理某個問題、決定邊啲不變量保證至關重要，並圍繞「令正確嘅寫法成為最順手嘅寫法」嚟進行架構設計。

Steel 嘅意義絕唔只係將 Minecraft 用 Rust 重寫一次然後宣稱佢更快。我希望佢嘅程式碼令人寫起上嚟舒心，更希望佢嘅底層基石喺面對第二個複雜用例時依然穩固，而唔係被迫推倒重來。

呢個並唔意味住要為永遠唔會發生嘅問題過度設計抽象，而係要先透徹理解問題本身，再選擇嗰個真正正確嘅最簡方案。

世界生成（World Generation）正正就係呢種設計哲學首次落地嘅地方。

## 透過「區塊金字塔」建構世界

Minecraft 並唔會喺單次遍歷入面直接生成一個完整區塊，而係令區塊依序推進通過一系列生成階段（Chunk Status / Stage）：定位結構（Structures）、選擇生物群系（Biomes）、塑造地形雜訊（Noise）、鋪設地表（Surface）、雕刻洞穴（Carvers）、放置礦石與樹木等地物（Features），以及傳播光照（Light）。每一個階段都要求目標區塊周圍一定範圍內嘅鄰居區塊已經抵達特定嘅前置階段。

我以前成日將呢種依賴關係想像成一棵樹：請求某個座標處嘅完整區塊，令佢去請求周圍嘅鄰居，再令鄰居去請求各自嘅鄰居，直到所有前置條件都滿足為止。但如果直接按呢種思路去寫，好快就會陷入遞歸泥沼：區塊 X 等待區塊 Y，而區塊 Y 最終又反過嚟請求區塊 X。

原版將佢嘅解決方案稱為**區塊金字塔（Chunk Pyramid）** 。起初我對呢個名一頭霧水，直到我真正理解咗佢所描述嘅結構。

一個區塊要抵達最終嘅 `Full`（完整）階段，依賴於周圍 23×23 範圍嘅區塊均已抵達 `Structure Starts`（結構起點）階段。後續階段所需嘅範圍逐層縮小：7×7，跟住係 5×5，然後係 3×3。去到最後幾個階段，就只需要中心區塊自身喇。將每一階段所需嘅最小區域層層疊放起嚟，恰好構成一座金字塔。

![以原版階段配色展示全部十二個區塊生成階段嘅等軸測區塊金字塔示意圖，由底部嘅 23×23 Empty 與 Structure Starts 區域逐層收窄至頂部嘅單個 Full 區塊。](@/assets/chunk-pyramid.svg "Steel 嘅累積區塊生成依賴金字塔")

*每一層展示咗該階段所需嘅最小區塊範圍。圖中嘅尺寸與半徑均為精確值，僅喺視覺寬度上做咗緊湊化處理。*

一旦從呢個視角睇問題，依賴關係就唔再係遞歸㗎喇。Steel 按順序逐階段推進，喺每個階段並行處理所有必需嘅區塊，然後再進入下一階段。喺實際運行中，鄰近嘅區塊請求會相互重疊，因此好多區塊嘅進度往往已經領先於金字塔所示嘅最低要求。起初每個階段都只係空操作（No-op），但睇住調度器有條不紊咁協調起成套系統，依然有一種秩序之美。

### 追逐原版特性相容（Parity）

由一開始，我哋嘅目標就係逐方塊嘅原版地形相容：給定相同嘅世界種子碼（Seed）、遊戲版本與座標，Steel 應當生成與原版分毫不差嘅方塊。

我哋由生物群系開始，隨後實現咗填充基礎地形嘅雜訊（Noise）階段。呢一步即刻暴露出整潔嘅階段流程圖背後隱藏嘅一個依賴：地形塑造需要讀取結構（Structure）相關嘅資訊。喺結構管線尚未完成期間，我哋喺自研提取器（[steel_extractor](/zh-hk/development/tools/steel_extractor/)）生成嘅原版參考世界入面暫時停用咗結構生成。咁樣既可以對已實現嘅地形邏輯進行嚴格測試，又唔使降低最終嘅相容性標準。

地表（Surface）階段會將雜訊階段生成嘅裸露石頭替換為玩家熟悉嘅方塊：草方塊、泥土、沙、雪塊等等。當我哋嘅地表實現接近尾聲時，2,500 個測試區塊入面幾乎所有區塊都同原版完全吻合。冇錯， **幾乎**。

唯獨有一個區塊對唔上。我哋順藤摸瓜一路排查，最終定位到一次距離打和嘅生物群系查找。原版將生物群系搜尋結果緩存喺線程局部狀態（Thread-local State）入面，因此打和時嘅選取結果可能會取決於該工作線程之前恰好生成過邊啲區塊。僅僅擁有相同嘅種子碼同座標，有時竟然唔足以喺原版入面決定唯一確定嘅輸出。

正正由嗰一刻起，我哋嘅目標變得更加精確：喺原版具有確定性嘅地方，Steel 應當嚴格重現原版；保留玩家所依賴嘅一切行為特性；而喺原版因為實現細節產生意外嘅非確定性時，只要唔改變遊戲機制本身，我哋就將其修正為確定性行為。

而家，Steel 使用區塊局部（Chunk-local）嘅生物群系緩存，令生成結果唔再受工作線程調度順序影響。為咗進行相容性測試，我哋亦相應修改咗原版提取器，令佢喺每個區塊生成前重置緩存，從而重現 Steel 嘅確定性行為。

地物（Features）階段則引入咗另一個非確定性來源。樹木、礦脈等地物可能會跨越區塊邊界，因此改變相鄰區塊嘅生成先後順序就可能改變最終嘅方塊放置結果。為咗令相容性對比具有實際意義，我哋嘅提取器會按照固定順序逐個生成參考區塊。

就算係咁，仍然有零星幾個方塊存在差異。排查線索最終指向咗原版地物程式碼入面基於雜湊（Hash-based）嘅集合類型——佢哋嘅迭代順序並唔穩定，但喺世界生成過程中，迭代順序會直接決定邊個方塊先被放置、邊個方塊隨後被覆蓋。我哋為呢啲操作賦予咗明確嘅確定性順序，並同步修改咗提取器以採用相同順序。

喺消除咗最後一個非確定性來源之後，所有測試區塊終於實現咗逐方塊嘅百分百吻合。

目前實體生成（Entity Spawning）階段仍保持停用狀態，因為 Steel 尚未實現世界上絕大多數實體嘅 AI 與行為邏輯。如果而家強行開啟該階段，或者靜默丟棄生成嘅實體，都會俾人一種「已經大功告成」嘅錯覺。因此，實體生成暫時唔包含喺目前嘅相容性聲明範圍內。

### 告別全局隊列嘅並行光照

喺各類實驗性 Minecraft 伺服器入面，光照系統長期以嚟都係最常缺失嘅一環。原因顯而易見：光照會跨越區塊邊界傳播，相鄰嘅兩個區塊如果喺冇協調嘅情況下同時傳播重疊嘅光照更新，就會產生數據競爭。原版雖然將光照計算移出咗主線程，但依然喺單線程光照引擎入面串行處理，令光照成為咗並行世界生成過程中嘅一大瓶頸。

模組社群早已透過 [Starlight](https://github.com/PaperMC/Starlight) 深入探索過呢個難題。喺 Starlight 停止作為獨立模組維護後，[ScalableLux](https://github.com/RelativityMC/ScalableLux) 作為分支延續咗佢嘅工作，並加入咗實驗性嘅並行模式。Steel 嘅光照引擎正正係汲取咗呢啲先行者嘅思想，但由零開始圍繞 Rust 嘅所有權模型與並行原語進行設計。各個區塊可以並行計算光照，同時由區塊調度器確保相互重疊嘅光照工作唔會發生衝突。

### 實測效能表現

區塊調度器與並行光照引擎嘅結合，帶嚟咗實打實嘅可量化成果。喺一部配備 Ryzen 9 9950X 嘅機器上，Steel 由零生成一片 10,201 個區塊嘅主世界區域，中位數耗時僅為**3.95 秒**；而使用 Chunky 預生成插件嘅 Fabric 伺服器則耗時**74.42 秒**。喺三次冷啟動測試中，Steel 平均每秒可生成**2,582 個區塊**，吞吐量達到 Fabric 嘅**18.8 倍**。

![展示三次冷啟動測試平均區塊生成吞吐量嘅水平棒形圖：Steel 達到 2,581.8 區塊/秒，而 Fabric 為 137.2 區塊/秒。](@/assets/benchmarks/chunk-generation-throughput.svg "三次冷啟動測試嘅區塊生成吞吐量對比")

當然，睇呢啲亮眼嘅數據需要結合具體背景：喺測試區間內，Steel 平均佔用咗 30.2 個邏輯 CPU 核心，而 Fabric 平均僅佔用咗 4.4 個。因此，呢項測試既衡量咗多核並行擴展能力，亦衡量咗單核執行效率。喺按 CPU 核心時間進行折算歸一化後，Steel 每 CPU 秒生成嘅區塊數依然係 Fabric 嘅**2.75 倍** 。

需要說明嘅係，呢個只係單部機器上針對世界生成場景嘅專項基準測試，並唔意味住 Steel 喺所有伺服器負載下都比原版快 18.8 倍；此外，測試中 Steel 未執行實體生成階段，而 Fabric 執行咗該階段。完整嘅測試方法、單次運行數據、記憶體佔用曲線、原始數據集、重現步驟以及更多限制說明，請參閱[完整基準測試報告](/zh-hk/reference/benchmarks/)。上述效能測試與前文所述嘅逐方塊相容性測試係相互獨立嘅。

## 令遊戲刻（Game Tick）保持流暢運轉

原版 Minecraft 最為人熟知嘅設計莫過於佢嘅單主線程模型。呢項設計提供咗一個極具價值嘅保證：喺遊戲刻（Game Tick）執行期間，成個世界嘅狀態唔會喺佢腳下發生改變。但代價係，任何唔相關嘅耗時操作都可能拖慢成部伺服器。

Steel 為核心玩法邏輯保留咗同步嘅遊戲刻模型，但將封包處理、區塊調度與區塊發送全部移出咗主遊戲刻。專用嘅封包工作線程會喺兩個遊戲刻之間嘅窗口期內持續處理遊戲封包，而唔係好似原版咁將所有封包積攢起嚟留到下一刻開頭集中批處理。當到達刻邊界時，Steel 會暫停接納新嘅遊戲封包，並將已接納嘅封包排空處理完畢，隨後喺穩定嘅世界狀態上推進區塊與實體邏輯，完成後再恢復封包接納。

與此同時，區塊調度器喺後台並行傳播載入票據（Tickets）並派發生成工作，區塊發送循環則負責打包已完成嘅區塊並傳輸俾客戶端。磁碟 I/O 與網絡 I/O 再都唔需要擠佔寶貴嘅遊戲刻時間預算。

呢個架構背後嘅準則非常純粹： **遊戲刻絕唔為等待非同步工作而阻塞。**

以玩家重生（Respawn）為例：目標位置嘅區塊必須準備就緒，玩家先可以安全咁出現喺嗰度；但如果令主線程原地等待區塊載入，伺服器上面嘅所有其他玩家同實體都會跟住卡住。Steel 嘅做法係建立一個非同步工作並喺每個遊戲刻檢查其狀態，一旦非同步準備工作完成，就喺明確定義嘅安全時間點同步執行玩家嘅傳送與生成。

咁樣既保留咗同步世界模型最核心嘅優勢——所有玩法狀態變更都發生喺明確嘅安全邊界上，又避免咗慢速磁碟讀取或區塊依賴將成部伺服器拖入全局停頓。

## 保留紅石系統入面嗰啲「有用嘅特性（Bug）」

紅石系統則呈現出截然相反嘅挑戰。原版入面嘅某些行為喺技術層面上純屬無心插柳嘅偶然產物，但多年以嚟早已俾紅石社群深入研究、整理成文檔，並化作各類紅石機器嘅基石。如果貿然「修復」佢哋，無數現實中嘅紅石機器就會徹底罷工。

一個典型嘅例子就係[位置性（Locationality）](https://www.youtube.com/watch?v=7gF5mbjFies)：同一個紅石裝置，僅僅因為擺放喺世界中嘅座標或朝向唔同，就可能表現出唔同嘅行為。其中一部分行為源於處理方塊更新時所使用嘅雜湊集合（HashSet）嘅迭代順序。喺程式員眼中呢個或許只係個實現細節，但喺生電與紅石玩家眼中，呢個就係遊戲機制嘅一部分。

因此，Steel 嘅紅石實現唔單止致力於還原設計預期內嘅規則，亦同樣注重保留玩家們所依賴嘅呢啲微妙特性。原版特性相容並唔意味住將所有古怪嘅行為都清理乾淨，而係要識得分邊啲「怪癖」早已昇華為遊戲特性。

## 喺插件誕生之前，先為插件做好設計

插件系統係我最想建構嘅功能之一，但亦係我絕對拒絕倉促上馬嘅部分。插件 API 幾乎會暴露伺服器嘅每一個角落，如果過早發佈並定型，錯誤嘅抽象設計可能會將項目束縛好幾年。喺我能夠負責任咁決定插件 API 應該作出邊啲承諾之前，Steel 首先必須成為一個紮實可靠嘅 Minecraft 伺服器。

我曾探索過 WebAssembly、各類腳本語言以及原生 Rust 插件。目前嘅演進方向係提供一套原生 Rust API，賦予擴展與伺服器本體同等嘅底層能力。喺此之上，原生插件依然可以透過內嵌 WebAssembly 或 JavaScript、Lua 等語言運行時，向上提供沙盒化或更高階嘅腳本開發環境。由於原生插件屬於受信任程式碼，因此 API 邊界嘅設計需要格外審慎。

Bukkit 與 Paper 多年嘅生態積累，已經充分展示咗伺服器擴展最常解決嘅問題領域。Steel 從呢啲實際用例中汲取咗靈感（例如伺服器與插件點樣使用[權限系統](/zh-hk/configuration/permissions/)），但唔會照搬 Bukkit 或 Paper 嘅公開 API。目前 Steel 尚唔支援插件，喺底層伺服器足夠成熟、能夠負責任咁兌現 API 承諾之前，我哋唔會貿然發佈插件介面。

## 點解選擇而家官宣 Steel

Steel 目前仍處於 Pre-Alpha 階段，前方仲有大量工作等待完成。我哋仲未有插件系統，好多原版機制仍喺度緊鑼密鼓咁補齊，隨住探索深入，我哋亦一定會遇到新嘅 Bug、尚未完善嘅機制以及需要重新審視嘅架構決策。

但 Steel 已經唔再係一個「或者有一日會變成伺服器」嘅玩具原型喇。佢係一個你今日就可以連接落去遊玩嘅伺服器，背後凝結咗九個月嘅研發積累、經過嚴格測試驗證嘅原版地形生成相容、可正常運作嘅核心玩法系統，以及一班不斷壯大嘅貢獻者團隊。

最近我邀請咗三位見習維護者加入團隊：Junky、Evald 同 purdze。我希望佢哋能共同推動項目行前，令 Steel 唔再過度依賴我一個人。呢一點喺當下尤為重要——因為我即將開始服兵役，喺接落嚟大約一年嘅時間入面，能夠投入到項目嘅時間會有所減少。不過大多數週末我依然會喺線上審閱程式碼、解答問題，並盡己所能繼續開發。

呢個亦係我選擇喺呢個時候正式公佈 Steel 嘅重要原因之一：呢個項目需要成長為一個超越我個人默默耕耘嘅開源社群工程。

## 關於 AI 輔助貢獻嘅說明

Steel 允許將 AI 作為輔助工具使用，但絕唔允許用佢取代貢獻者自己嘅思考。無論你係用佢查詢 API、理解編譯器報錯，定係探討可行嘅實現思路，你都必須透徹理解自己提交嘅每一行程式碼，並能夠清晰咁闡明背後嘅設計考量。

我哋唔接受完全由 AI 自主生成嘅 Pull Request，貢獻者必須親自撰寫並理解自己嘅 PR 描述。我哋嘅[貢獻指南](/zh-hk/development/start-contributing/)詳細列出咗相關規範與入門方式。
