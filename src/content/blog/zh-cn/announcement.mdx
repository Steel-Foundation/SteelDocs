SteelMC 是一个用 Rust 编写的“全新” Minecraft 服务端。不用去更新 [*距离上一个 Rust Minecraft 服务端诞生已经过去了多少天*](https://dayssincelastrustmcserver.com/) 了——早在 2025 年 10 月 16 日，我们就已经被收录在上面了。

我一直不喜欢在代码仓库刚创建的那一刻就大张旗鼓地官宣项目。因为大家的反应往往是“挺酷的，等它真能跑起来再叫我”。而等到项目真的做出点名堂时，它要么已经半途夭折，要么早就被大家遗忘了。

所以我选择了等待。

Steel 在 2026 年 5 月 20 日首次实现了逐方块（Block-for-block）的原版地形生成对齐。目前的一致性测试套件覆盖了 7,500 个随机抽取的区块：主世界、下界与末地三个维度各 2,500 个。

Steel 目前仍处于 Pre-Alpha 阶段，但你现在已经可以连接进服、探索持久化生成的世界、与方块和物品栏交互，并在现有基础之上开始建造。

过去这九个月的大部分精力，都投入到了玩家进服时几乎察觉不到的底层系统中。随着这些底层基建走向成熟，后续新增游戏玩法所需的配套支撑会越来越少，越来越多的工作成果将直观地体现在游戏体验中。

## 简而言之：Steel 今天能做什么

Steel 的目标是紧跟 Minecraft Java 版最新正式版，目前适配版本为 **26.2**。客户端可以加入服务器、加载生成的世界、移动与交互、使用物品栏与命令，并在之后重新回到已保存的世界。这些系统是在一个持久化的多人联机服务端中协同运作的，而不仅仅是孤立的网络协议或世界生成演示。

生存模式玩法目前尚未完善，仅有少数几种实体类型实现了完整的行为逻辑，且 Steel 尚未达到完全的原版特性对齐或协议对齐。插件系统也暂未推出，为 Paper、Bukkit、Fabric、Forge 或 NeoForge 编写的扩展均无法直接使用。我绝不会夸下海口让你明天就把生产环境里的 Paper 服务端替换成 Steel。

## 我为什么要发起 Steel

在开始写 Steel 之前，我曾长期为 [PumpkinMC](https://github.com/Pumpkin-MC/Pumpkin) 贡献代码。Pumpkin 是我开始用 Rust 编写 Minecraft 服务端的原因，下文提到的任何内容都绝非对 Pumpkin 贡献者们的批评。这些记述基于 2025 年 10 月前后的 Pumpkin 代码库，如今它可能已经发生了很大变化。

我热爱 Rust 的一点在于，随着你对这门语言理解的深入，它的种种限制会变得越来越合乎情理。一个令人抓狂的编译器报错，往往是在保护你避开某个尚未考虑到的边界情况。这种“有人已经把问题深思熟虑过了”的感觉，开始塑造我对自己所构建系统的期望。

我在那里实现了红石系统，并重写了物品栏系统。在贡献代码的过程中，我逐渐意识到自己在对待底层基础系统时有着不同的取向：我希望先退后一步，研究清楚后续会遇到的复杂场景，确保底层架构不仅能应付眼前的第一个用例，还能支撑起未来的演进。

当 Pumpkin 开始为世界生成器添加树木时，这种理念差异变得尤为明显。当时每个区块都是孤立生成的——这在大多数时候没问题，但一旦靠近区块边界的树需要把树叶放置到相邻区块中，问题就来了。我花了大约一个月研究这个问题，并逐渐意识到它的本质是如何协调一整个区域的生成流程，而不单单是放一棵树。项目最终合并了另一个能解决燃眉之急的方案。两种优先级都没有错，但那件事让我明确意识到，我想围绕另一种理念去构建服务端。

于是我启动了 Steel，起初并没有抱太高预期。我动手实现的第一件事，就是在参与 Pumpkin 时一直心心念念的方块注册表（Block Registry）与方块属性（Property）系统。这是我第一次能够深入研究原版是如何处理某个问题的、决定哪些不变量保证至关重要，并围绕“让正确的写法成为最顺手的写法”来进行架构设计。

Steel 的意义绝不只是把 Minecraft 用 Rust 重写一遍然后宣称它更快。我希望它的代码让人写起来舒心，更希望它的底层基石在面对第二个复杂用例时依然稳固，而不是被迫推倒重来。

这并不意味着要为永远不会发生的问题过度设计抽象，而是要先透彻理解问题本身，再选择那个真正正确的最简方案。

世界生成（World Generation）正是这一设计哲学首次落地的地方。

## 通过“区块金字塔”构建世界

Minecraft 并不会在单次遍历中直接生成一个完整区块，而是让区块依次推进通过一系列生成阶段（Chunk Status / Stage）：定位结构（Structures）、选择生物群系（Biomes）、塑造地形噪声（Noise）、铺设地表（Surface）、雕刻洞穴（Carvers）、放置矿石与树木等地物（Features），以及传播光照（Light）。每一个阶段都要求目标区块周围一定范围内的邻居区块已经抵达特定的前置阶段。

我过去常常把这种依赖关系想象成一棵树：请求某个坐标处的完整区块，让它去请求周围的邻居，再让邻居去请求各自的邻居，直到所有前置条件都满足。但如果直接按这种思路去写，很快就会陷入递归泥潭：区块 X 等待区块 Y，而区块 Y 最终又反过来请求区块 X。

原版将它的解决方案称为**区块金字塔（Chunk Pyramid）** 。起初我对这个名字一头雾水，直到我真正理解了它所描述的结构。

一个区块要抵达最终的 `Full`（完整）阶段，依赖于周围 23×23 范围的区块均已抵达 `Structure Starts`（结构起点）阶段。后续阶段所需的范围逐层缩小：7×7，接着是 5×5，然后是 3×3。到了最后几个阶段，就只需要中心区块自身了。把每一阶段所需的最小区域层层叠放起来，恰好构成一座金字塔。

![以原版阶段配色展示全部十二个区块生成阶段的等轴测区块金字塔示意图，从底部的 23×23 Empty 与 Structure Starts 区域逐层收窄至顶部的单个 Full 区块。](@/assets/chunk-pyramid.svg "Steel 的累积区块生成依赖金字塔")

*每一层展示了该阶段所需的最小区块范围。图中的尺寸与半径均为精确值，仅在视觉宽度上做了紧凑化处理。*

一旦从这个视角看待问题，依赖关系就不再是递归的了。Steel 按顺序逐阶段推进，在每个阶段并行处理所有必需的区块，然后再进入下一阶段。在实际运行中，邻近的区块请求会相互重叠，因此许多区块的进度往往已经领先于金字塔所示的最低要求。起初每个阶段都只是空操作（No-op），但看着调度器有条不紊地协调起整套系统，依然有一种秩序之美。

### 追逐原版特性对齐（Parity）

从一开始，我们的目标就是逐方块的原版地形对齐：给定相同的世界种子（Seed）、游戏版本与坐标，Steel 应当生成与原版分毫不差的方块。

我们从生物群系开始，随后实现了填充基础地形的噪声（Noise）阶段。这立刻暴露出了整洁的阶段流程图背后隐藏的一个依赖：地形塑造需要读取结构（Structure）相关的信息。在结构管线尚未完成期间，我们在自研提取器（[steel_extractor](/zh-cn/development/tools/steel_extractor/)）生成的原版参考世界中临时禁用了结构生成。这样既能对已实现的地形逻辑进行严格测试，又不必降低最终的一致性标准。

地表（Surface）阶段会将噪声阶段生成的裸露石头替换为玩家熟悉的方块：草方块、泥土、沙子、雪块等等。当我们的地表实现接近尾声时，2,500 个测试区块中几乎所有区块都与原版完全吻合。没错， **几乎**。

唯独有一个区块对不上。我们顺藤摸瓜一路排查，最终定位到了一次距离平局的生物群系查找。原版将生物群系搜索结果缓存在线程局部状态（Thread-local State）中，因此平局时的选取结果可能会取决于该工作线程此前恰好生成过哪些区块。仅仅拥有相同的种子和坐标，有时竟不足以在原版中决定唯一确定的输出。

正是从那一刻起，我们的目标变得更加精确：在原版具有确定性的地方，Steel 应当严格复现原版；保留玩家所依赖的一切行为特性；而在原版因实现细节产生意外的非确定性时，只要不改变游戏机制本身，我们就将其修正为确定性行为。

现在，Steel 使用区块局部（Chunk-local）的生物群系缓存，使生成结果不再受工作线程调度顺序的影响。为了进行一致性测试，我们也相应修改了原版提取器，使其在每个区块生成前重置缓存，从而复现 Steel 的确定性行为。

地物（Features）阶段则引入了另一个非确定性来源。树木、矿脉等地物可能会跨越区块边界，因此改变相邻区块的生成先后顺序就可能改变最终的方块放置结果。为了让一致性对比具有实际意义，我们的提取器会按照固定顺序逐个生成参考区块。

即便如此，仍有零星几个方块存在差异。排查线索最终指向了原版地物代码中基于哈希（Hash-based）的集合类型——它们的迭代顺序并不稳定，但在世界生成过程中，迭代顺序会直接决定哪个方块先被放置、哪个方块随后被覆盖。我们为这些操作赋予了显式的确定性顺序，并同步修改了提取器以采用相同顺序。

在消除了最后一个非确定性来源后，所有测试区块终于实现了逐方块的百分百吻合。

目前实体生成（Entity Spawning）阶段仍保持禁用状态，因为 Steel 尚未实现世界上绝大多数实体的 AI 与行为逻辑。如果现在强行开启该阶段，或是静默丢弃生成的实体，都会给人一种“已经大功告成”的错觉。因此，实体生成暂不包含在当前的一致性声明范围内。

### 告别全局队列的并行光照

在各类实验性 Minecraft 服务端中，光照系统长期以来都是最常缺失的一环。原因显而易见：光照会跨越区块边界传播，相邻的两个区块如果在没有协调的情况下同时传播重叠的光照更新，就会产生数据竞争。原版虽然将光照计算移出了主线程，但依然在单线程光照引擎中串行处理，这使光照成为了并行世界生成过程中的一大瓶颈。

模组社区早已通过 [Starlight](https://github.com/PaperMC/Starlight) 深入探索过这一难题。在 Starlight 停止作为独立模组维护后，[ScalableLux](https://github.com/RelativityMC/ScalableLux) 作为分支延续了它的工作，并加入了实验性的并行模式。Steel 的光照引擎正是汲取了这些先行者的思想，但从零开始围绕 Rust 的所有权模型与并发原语进行设计。各个区块可以并行计算光照，同时由区块调度器确保相互重叠的光照任务不会发生冲突。

### 实测性能表现

区块调度器与并行光照引擎的结合，带来了实打实的可量化成果。在一台搭载 Ryzen 9 9950X 的机器上，Steel 从零生成一片 10,201 个区块的主世界区域，中位耗时仅为**3.95 秒**；而使用 Chunky 预生成插件的 Fabric 服务端则耗时**74.42 秒**。在三次冷启动测试中，Steel 平均每秒可生成**2,582 个区块**，吞吐量达到 Fabric 的**18.8 倍**。

![展示三次冷启动测试平均区块生成吞吐量的水平柱状图：Steel 达到 2,581.8 区块/秒，而 Fabric 为 137.2 区块/秒。](@/assets/benchmarks/chunk-generation-throughput.svg "三次冷启动测试的区块生成吞吐量对比")

当然，看待这些亮眼的数据需要结合具体背景：在测试区间内，Steel 平均占用了 30.2 个逻辑 CPU 核心，而 Fabric 平均仅占用了 4.4 个。因此，这项测试既衡量了多核并行扩展能力，也衡量了单核执行效率。在按 CPU 核心时间进行折算归一化后，Steel 每 CPU 秒生成的区块数依然是 Fabric 的**2.75 倍** 。

需要说明的是，这只是单台机器上针对世界生成场景的专项基准测试，并不意味着 Steel 在所有服务端负载下都比原版快 18.8 倍；此外，测试中 Steel 未执行实体生成阶段，而 Fabric 执行了该阶段。完整的测试方法、单次运行数据、内存占用曲线、原始数据集、复现步骤以及更多局限性说明，请参阅[完整基准测试报告](/zh-cn/reference/benchmarks/)。上述性能测试与前文所述的逐方块一致性测试是相互独立的。

## 让游戏刻（Game Tick）保持流畅运转

原版 Minecraft 最为人熟知的设计莫过于它的单主线程模型。这一设计提供了一项极具价值的保证：在游戏刻（Game Tick）执行期间，整个世界的状态不会在它脚下发生改变。但代价是，任何耗时操作都可能拖慢整台服务器。

Steel 为核心玩法逻辑保留了同步的游戏刻模型，但将数据包处理、区块调度与区块发送全部移出了主游戏刻。专用的数据包工作线程会在两个游戏刻之间的窗口期内持续处理游戏数据包，而不是像原版那样把所有数据包积攒起来留到下一刻开头集中批处理。当到达刻边界时，Steel 会暂停接纳新的游戏数据包，并将已接纳的数据包排空处理完毕，随后在稳定的世界状态上推进区块与实体逻辑，完成后再恢复数据包接纳。

与此同时，区块调度器在后台并行传播加载票据（Tickets）并派发生成任务，区块发送循环则负责打包已完成的区块并传输给客户端。磁盘 I/O 与网络 I/O 再也不需要挤占宝贵的游戏刻时间预算。

<TickArchitecture />

这一架构背后的准则非常纯粹： **游戏刻绝不为等待异步任务而阻塞。**

以玩家重生（Respawn）为例：目标位置的区块必须准备就绪，玩家才能安全地出现在那里；但如果让主线程原地等待区块加载，服务器上的所有其他玩家和实体都会跟着卡住。Steel 的做法是创建一个异步任务并在每个游戏刻检查其状态，一旦异步准备工作完成，就在明确定义的安全时间点同步执行玩家的传送与生成。

这样既保留了同步世界模型最核心的优势——所有玩法状态变更都发生在明确的安全边界上，又避免了慢速磁盘读取或区块依赖把整台服务器拖入全局停顿。

## 保留红石系统中那些“有用的特性（Bug）”

红石系统则呈现出截然相反的挑战。原版中的某些行为在技术层面上纯属无心插柳的偶然产物，但多年以来早已被红石社区深入研究、整理成文档，并化作了各类红石机器的基石。如果贸然“修复”它们，无数现实中的红石机器就会彻底罢工。

一个典型的例子就是[位置性（Locationality）](https://www.youtube.com/watch?v=7gF5mbjFies)：同一个红石装置，仅仅因为摆放在世界中的坐标或朝向不同，就可能表现出不同的行为。其中一部分行为源于处理方块更新时所使用的哈希集合（HashSet）的迭代顺序。在程序员眼中这或许只是个实现细节，但在生电与红石玩家眼中，这就是游戏机制的一部分。

因此，Steel 的红石实现不仅致力于还原设计预期内的规则，也同样注重保留玩家们所依赖的这些微妙特性。原版特性对齐并不意味着把所有古怪的行为都清理干净，而是要懂得分辨哪些“怪癖”早已升华为游戏特性。

## 在插件诞生之前，先为插件做好设计

插件系统是我最想构建的功能之一，但也是我绝对拒绝仓促上马的部分。插件 API 几乎会暴露服务端的每一个角落，如果过早发布并定型，错误的抽象设计可能会把项目束缚好几年。在我能够负责任地决定插件 API 应该作出哪些承诺之前，Steel 首先必须成为一个扎实可靠的 Minecraft 服务端。

我曾探索过 WebAssembly、各类脚本语言以及原生 Rust 插件。目前的演进方向是提供一套原生 Rust API，赋予扩展与服务端本体同等的底层能力。在此之上，原生插件依然可以通过内嵌 WebAssembly 或 JavaScript、Lua 等语言运行时，向上提供沙盒化或更高层的脚本开发环境。由于原生插件属于受信任代码，因此 API 边界的设计需要格外审慎。

Bukkit 与 Paper 多年的生态积累，已经充分展示了服务端扩展最常解决的问题域。Steel 从这些实际用例中汲取了灵感（例如服务端与插件如何使用[权限系统](/zh-cn/configuration/permissions/)），但不会照搬 Bukkit 或 Paper 的公开 API。目前 Steel 尚不支持插件，在底层服务端足够成熟、能够负责任地兑现 API 承诺之前，我们不会贸然发布插件接口。

## 为什么选择现在官宣 Steel

Steel 目前仍处于 Pre-Alpha 阶段，前方还有大量工作等待完成。我们还没有插件系统，许多原版机制仍在紧锣密鼓地补齐，随着探索深入，我们也一定会遇到新的 Bug、尚未完善的机制以及需要重新审视的架构决策。

但 Steel 已经不再是一个“也许有一天能变成服务端”的玩具原型了。它是一个你今天就能连接进去游玩的服务器，背后凝结了九个月的研发积累、经过严格测试验证的原版地形生成对齐、可正常运作的核心玩法系统，以及一群不断壮大的贡献者团队。

最近我邀请了三位实习维护者加入团队：Junky、Evald 和 purdze。我希望他们能共同推动项目前进，让 Steel 不再过度依赖我一个人。这一点在当下尤为重要——因为我即将开始服兵役，在接下来大约一年的时间里，能够投入到项目中的时间会有所减少。不过大多数周末我依然会在线审阅代码、解答问题，并尽己所能继续开发。

这也是我选择在此时正式公布 Steel 的重要原因之一：这个项目需要成长为一个超越我个人默默耕耘的开源社区工程。

## 关于 AI 辅助贡献的说明

Steel 允许将 AI 作为辅助工具使用，但绝不允许用它替代贡献者自己的思考。无论你是用它查询 API、理解编译器报错，还是探讨可行的实现思路，你都必须透彻理解自己提交的每一行代码，并能够清晰地阐明背后的设计考量。

我们不接受完全由 AI 自主生成的 Pull Request，贡献者必须亲自撰写并理解自己的 PR 描述。我们的[贡献指南](/zh-cn/development/start-contributing/)详细列出了相关规范与入门方式。
