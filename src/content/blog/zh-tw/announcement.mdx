SteelMC 是一個以 Rust 撰寫的「全新」Minecraft 伺服器。不用去更新 [*距離上一個 Rust Minecraft 伺服器誕生已經過了多少天*](https://dayssincelastrustmcserver.com/) 了——早在 2025 年 10 月 16 日，我們就已經被收錄在上面了。

我一直不喜歡在儲存庫剛建立的那一刻就大張旗鼓地宣佈專案。因為大家的反應往往是「很酷喔，等它真的能跑起來再告訴我們」。而等到專案真的做出一點成果時，它要嘛已經半途夭折，要嘛早就被大家遺忘了。

所以我選擇了等待。

Steel 在 2026 年 5 月 20 日首次實現了逐方塊（Block-for-block）的原版地形生成相容。目前的相容性測試套件涵蓋了 7,500 個隨機抽取的區塊：主世界、地獄与終界三個維度各 2,500 個。

Steel 目前仍處於 Pre-Alpha 階段，但你現在已經可以連線進入伺服器、探索持久化生成的世界、與方塊和物品欄互動，並在現有基礎之上開始建造。

過去這九個月的大部分心力，都投入到了玩家進入伺服器時幾乎察覺不到的底層系統中。隨著這些底層基礎設施走向成熟，後續新增遊戲玩法所需的配套支撐會越來越少，越來越多工作成果將直接呈現在遊戲體驗中。

## 簡而言之：Steel 今天能做什麼

Steel 的目標是緊跟 Minecraft Java 版最新正式版，目前鎖定支援版本為 **26.2**。用戶端可以加入伺服器、載入生成的世界、移動與互動、使用物品欄與指令，並在之後重新回到已儲存的世界。這些系統是在一個持久化的多人連線伺服器中協同運作的，而不僅僅是孤立的網路協定或世界生成展示。

生存模式玩法目前尚未完善，僅有少數幾種實體類型實作了完整的行為邏輯，且 Steel 尚未達到完全的原版特性相容或協定相容。外掛（Plugin）系統也暫未推出，為 Paper、Bukkit、Fabric、Forge 或 NeoForge 撰寫的擴充功能均無法直接使用。我絕不會誇下海口要你明天就把正式環境裡的 Paper 伺服器替換成 Steel。

## 我為什麼要發起 Steel

在開始寫 Steel 之前，我曾長期為 [PumpkinMC](https://github.com/Pumpkin-MC/Pumpkin) 貢獻程式碼。Pumpkin 是我開始用 Rust 撰寫 Minecraft 伺服器的契機，下文提到的任何內容都絕非對 Pumpkin 貢獻者們的批評。這些記述基於 2025 年 10 月前後的 Pumpkin 程式碼庫，如今它可能已經有了很大的變化。

我熱愛 Rust 的一點在於，隨著你對這門語言理解的深入，它的種種限制會變得越來越合情合理。一個令人挫折的編譯器錯誤，往往是在保護你避開某個尚未考慮到的邊界情況。這種「有人已經把問題深思熟慮過了」的感覺，開始塑造我對自己所建構系統的期望。

我在那裡實作了紅石系統，並重寫了物品欄系統。在貢獻程式碼的過程中，我逐漸意識到自己在對待底層基礎系統時有著不同的取向：我希望先退後一步，研究清楚後續會遇到的複雜情境，確保底層架構不僅能應付眼前的第一個使用案例，還能支撐起未來的演進。

當 Pumpkin 開始為世界生成器加入樹木時，這種理念差異變得格外明顯。當時每個區塊都是孤立生成的——這在大多數時候沒問題，但一旦靠近區塊邊界的樹需要把樹葉放置到相鄰區塊中，問題就來了。我花了大約一個月研究這個問題，並逐漸意識到它的本質是如何協調一整個區域的生成流程，而不單單是放一棵樹。專案最終合併了另一個能解決燃眉之急的方案。兩種優先順序都沒有錯，但那件事讓我明確意識到，我想圍繞另一種理念去建構伺服器。

於是我啟動了 Steel，起初並沒有抱太高的預期。我動手實作的第一件事，就是在參與 Pumpkin 時一直心心念念的方塊註冊表（Block Registry）與方塊屬性（Property）系統。這是我第一次能夠深入研究原版是如何處理某個問題的、決定哪些不變量保證至關重要，並圍繞「讓正確的寫法成為最順手的寫法」來進行架構設計。

Steel 的意義絕不只是把 Minecraft 用 Rust 重寫一遍然後宣稱它更快。我希望它的程式碼讓人寫起來舒心，更希望它的底層基石在面對第二個複雜使用案例時依然穩固，而不是被迫推倒重來。

這並不意味著要為永遠不會發生的問題過度設計抽象，而是要先透徹理解問題本身，再選擇那個真正正確的最簡方案。

世界生成（World Generation）正是這一設計哲學首次落地的地方。

## 透過「區塊金字塔」建構世界

Minecraft 並不會在單次遍歷中直接生成一個完整區塊，而是讓區塊依序推進通過一系列生成階段（Chunk Status / Stage）：定位結構（Structures）、選擇生態域（Biomes）、塑造地形雜訊（Noise）、鋪設地表（Surface）、雕刻洞穴（Carvers）、放置礦石與樹木等特徵（Features），以及傳播光照（Light）。每一個階段都要求目標區塊周圍一定範圍內的鄰居區塊已經抵達特定的前置階段。

我過去常常把這種相依關係想像成一棵樹：請求某個座標處的完整區塊，讓它去請求周圍的鄰居，再讓鄰居去請求各自的鄰居，直到所有前置條件都滿足。但如果直接按這種思路去寫，很快就會陷入遞迴泥淖：區塊 X 等待區塊 Y，而區塊 Y 最終又反過來請求區塊 X。

原版將它的解決方案稱為**區塊金字塔（Chunk Pyramid）** 。起初我對這個名字一頭霧水，直到我真正理解了它所描述的結構。

一個區塊要抵達最終的 `Full`（完整）階段，相依於周圍 23×23 範圍的區塊均已抵達 `Structure Starts`（結構起點）階段。後續階段所需的範圍逐層縮小：7×7，接著是 5×5，然後是 3×3。到了最後幾個階段，就只需要中心區塊自身了。把每一階段所需的最小區域層層疊放起來，恰好構成一座金字塔。

![以原版階段配色展示全部十二個區塊生成階段的等軸測區塊金字塔示意圖，從底部的 23×23 Empty 與 Structure Starts 區域逐層收窄至頂部的單個 Full 區塊。](@/assets/chunk-pyramid.svg "Steel 的累積區塊生成相依金字塔")

*每一層展示了該階段所需的最小區塊範圍。圖中的尺寸與半徑均為精確值，僅在視覺寬度上做了緊湊化處理。*

一旦從這個視角看待問題，相依關係就不再是遞迴的了。Steel 依序逐階段推進，在每個階段並行處理所有必需的區塊，然後再進入下一階段。在實際運作中，鄰近的區塊請求會相互重疊，因此許多區塊的進度往往已經領先於金字塔所示的最低要求。起初每個階段都只是空操作（No-op），但看著排程器有條不紊地協調起整套系統，依然有一種秩序之美。

### 追逐原版特性相容（Parity）

從一開始，我們的目標就是逐方塊的原版地形相容：給定相同的世界種子碼（Seed）、遊戲版本與座標，Steel 應當生成與原版分毫不差的方塊。

我們從生態域開始，隨後實作了填充基礎地形的雜訊（Noise）階段。這立刻暴露出了整潔的階段流程圖背後隱藏的一個相依性：地形塑造需要讀取結構（Structure）相關的資訊。在結構管線尚未完成期間，我們在自研提取器（[steel_extractor](/zh-tw/development/tools/steel_extractor/)）生成的原版參考世界中暫時停用了結構生成。這樣既能對已實作的地形邏輯進行嚴格測試，又不必降低最終的相容性標準。

地表（Surface）階段會將雜訊階段生成的裸露石頭替換為玩家熟悉的方塊：草地、泥土、沙子、雪塊等等。當我們的地表實作接近尾聲時，2,500 個測試區塊中幾乎所有區塊都與原版完全吻合。沒錯， **幾乎**。

唯獨有一個區塊對不上。我們抽絲剝繭一路排查，最終定位到了一次距離平手的生態域查找。原版將生態域搜尋結果快取在執行緒局部狀態（Thread-local State）中，因此平手時的選取結果可能會取決於該工作執行緒先前恰好生成過哪些區塊。僅僅擁有相同的種子碼和座標，有時竟不足以在原版中決定唯一確定的輸出。

正是從那一刻起，我們的目標變得更加精確：在原版具有確定性的地方，Steel 應當嚴格重現原版；保留玩家所依賴的一切行為特性；而在原版因實作細節產生意外的非確定性時，只要不改變遊戲機制本身，我們就將其修正為確定性行為。

現在，Steel 使用區塊局部（Chunk-local）的生態域快取，使生成結果不再受工作執行緒排程順序的影響。為了進行相容性測試，我們也相應修改了原版提取器，使其在每個區塊生成前重設快取，從而重現 Steel 的確定性行為。

特徵（Features）階段則引入了另一個非確定性來源。樹木、礦脈等特徵可能會跨越區塊邊界，因此改變相鄰區塊的生成先後順序就可能改變最終的方塊放置結果。為了讓相容性對比具有實際意義，我們的提取器會按照固定順序逐個生成參考區塊。

即便如此，仍有零星幾個方塊存在差異。排查線索最終指向了原版特徵程式碼中基於雜湊（Hash-based）的集合類型——它們的迭代順序並不穩定，但在世界生成過程中，迭代順序會直接決定哪個方塊先被放置、哪個方塊隨後被覆蓋。我們為這些操作賦予了明確的確定性順序，並同步修改了提取器以採用相同順序。

在消除了最後一個非確定性來源後，所有測試區塊終於實現了逐方塊的百分百吻合。

目前實體生成（Entity Spawning）階段仍保持停用狀態，因為 Steel 尚未實作世界上絕大多數實體的 AI 與行為邏輯。如果現在強行開啟該階段，或是靜默捨棄生成的實體，都會給人一種「已經大功告成」的錯覺。因此，實體生成暫不包含在目前的相容性聲明範圍內。

### 告別全域佇列的並行光照

在各類實驗性 Minecraft 伺服器中，光照系統長期以來都是最常缺失的一環。原因顯而易見：光照會跨越區塊邊界傳播，相鄰的兩個區塊如果在沒有協調的情況下同時傳播重疊的光照更新，就會產生資料競爭。原版雖然將光照計算移出了主執行緒，但依然在單執行緒光照引擎中循序處理，這使光照成為了並行世界生成過程中的一大瓶頸。

模組社群早已透過 [Starlight](https://github.com/PaperMC/Starlight) 深入探索過這一難題。在 Starlight 停止作為獨立模組維護後，[ScalableLux](https://github.com/RelativityMC/ScalableLux) 作為分支延續了它的工作，並加入了實驗性的並行模式。Steel 的光照引擎正是汲取了這些先行者的思想，但從零開始圍繞 Rust 的所有權模型與並行原語進行設計。各個區塊可以並行計算光照，同時由區塊排程器確保相互重疊的光照工作不會發生衝突。

### 實測效能表現

區塊排程器與並行光照引擎的結合，帶來了實打實的可量化成果。在一台搭載 Ryzen 9 9950X 的機器上，Steel 從零生成一片 10,201 個區塊的主世界區域，中位數耗時僅為**3.95 秒**；而使用 Chunky 預生成外掛的 Fabric 伺服器則耗時**74.42 秒**。在三次冷啟動測試中，Steel 平均每秒可生成**2,582 個區塊**，吞吐量達到 Fabric 的**18.8 倍**。

![展示三次冷啟動測試平均區塊生成吞吐量的水平長條圖：Steel 達到 2,581.8 區塊/秒，而 Fabric 為 137.2 區塊/秒。](@/assets/benchmarks/chunk-generation-throughput.svg "三次冷啟動測試的區塊生成吞吐量對比")

當然，看待這些亮眼的數據需要結合具體背景：在測試區間內，Steel 平均使用了 30.2 個邏輯 CPU 核心，而 Fabric 平均僅使用了 4.4 個。因此，這項測試既衡量了多核心並行擴展能力，也衡量了單核心執行效率。在依 CPU 核心時間進行折算正規化後，Steel 每 CPU 秒生成的區塊數依然是 Fabric 的**2.75 倍** 。

需要說明的是，這只是單台機器上針對世界生成情境的專項基準測試，並不意味著 Steel 在所有伺服器負載下都比原版快 18.8 倍；此外，測試中 Steel 未執行實體生成階段，而 Fabric 執行了該階段。完整的測試方法、單次執行數據、記憶體使用曲線、原始資料集、重現步驟以及更多限制說明，請參閱[完整基準測試報告](/zh-tw/reference/benchmarks/)。上述效能測試與前文所述的逐方塊相容性測試是相互獨立的。

## 讓遊戲刻（Game Tick）保持流暢運轉

原版 Minecraft 最為人熟知的設計莫過於它的單一主執行緒模型。這一設計提供了一項極具價值的保證：在遊戲刻（Game Tick）執行期間，整個世界的狀態不會在它腳下發生改變。但代價是，任何不相關的耗時操作都可能拖慢整台伺服器。

Steel 為核心玩法邏輯保留了同步的遊戲刻模型，但將封包處理、區塊排程與區塊傳送全部移出了主遊戲刻。專用的封包工作執行緒會在兩個遊戲刻之間的視窗期內持續處理遊戲封包，而不是像原版那樣把所有封包累積起來留到下一刻開頭集中批次處理。當到達刻邊界時，Steel 會暫停接納新的遊戲封包，並將已接納的封包排空處理完畢，隨後在穩定的世界狀態上推進區塊與實體邏輯，完成後再恢復封包接納。

與此同時，區塊排程器在背景並行傳播載入票證（Tickets）並派發生成工作，區塊傳送迴圈則負責打包已完成的區塊並傳輸給用戶端。磁碟 I/O 與網路 I/O 再也不需要佔用寶貴的遊戲刻時間預算。

<TickArchitecture />

這一架構背後的準則非常純粹： **遊戲刻絕不為等待非同步工作而阻塞。**

以玩家重生（Respawn）為例：目標位置的區塊必須準備就緒，玩家才能安全地出現在那裡；但如果讓主執行緒原地等待區塊載入，伺服器上的所有其他玩家和實體都會跟著卡住。Steel 的做法是建立一個非同步工作並在每個遊戲刻檢查其狀態，一旦非同步準備工作完成，就在明確定義的安全時間點同步執行玩家的傳送與生成。

這樣既保留了同步世界模型最核心的優勢——所有玩法狀態變更都發生在明確的安全邊界上，又避免了慢速磁碟讀取或區塊相依性把整台伺服器拖入全域停頓。

## 保留紅石系統中那些「有用的特性（Bug）」

紅石系統則呈現出截然相反的挑戰。原版中的某些行為在技術層面上純屬無心插柳的偶然產物，但多年以來早已被紅石社群深入研究、整理成文件，並化作了各類紅石機械的基石。如果貿然「修復」它們，無數現實中的紅石機械就會徹底停擺。

一個典型的例子就是[位置性（Locationality）](https://www.youtube.com/watch?v=7gF5mbjFies)：同一個紅石裝置，僅僅因為擺放在世界中的座標或朝向不同，就可能表現出不同的行為。其中一部分行為源於處理方塊更新時所使用的雜湊集合（HashSet）的迭代順序。在程式設計師眼中這或許只是個實作細節，但在技術型與紅石玩家眼中，這就是遊戲機制的一部分。

因此，Steel 的紅石實作不僅致力於還原設計預期內的規則，也同樣注重保留玩家們所依賴的這些微妙特性。原版特性相容並不意味著把所有古怪的行為都清理乾淨，而是要懂得分辨哪些「怪癖」早已昇華為遊戲特性。

## 在外掛誕生之前，先為外掛做好設計

外掛系統是我最想建構的功能之一，但也是我絕對拒絕倉促上陣的部分。外掛 API 幾乎會暴露伺服器的每一個角落，如果過早發佈並定型，錯誤的抽象設計可能會把專案束縛好幾年。在我能夠負責任地決定外掛 API 應該作出哪些承諾之前，Steel 首先必須成為一個紮實可靠的 Minecraft 伺服器。

我曾探索過 WebAssembly、各類腳本語言以及原生 Rust 外掛。目前的演進方向是提供一套原生 Rust API，賦予擴充功能與伺服器本體同等的底層能力。在此之上，原生外掛依然可以透過內嵌 WebAssembly 或 JavaScript、Lua 等語言執行期，向上提供沙盒化或更高階的腳本開發環境。由於原生外掛屬於受信任程式碼，因此 API 邊界的設計需要格外審慎。

Bukkit 與 Paper 多年的生態積累，已經充分展示了伺服器擴充功能最常解決的問題領域。Steel 從這些實際使用案例中汲取了靈感（例如伺服器與外掛如何使用[權限系統](/zh-tw/configuration/permissions/)），但不會照搬 Bukkit 或 Paper 的公開 API。目前 Steel 尚不支援外掛，在底層伺服器足夠成熟、能夠負責任地兌現 API 承諾之前，我們不會貿然發佈外掛介面。

## 為什麼選擇現在宣佈 Steel

Steel 目前仍處於 Pre-Alpha 階段，前方還有大量工作等待完成。我們還沒有外掛系統，許多原版機制仍在緊鑼密鼓地補齊，隨著探索深入，我們也一定會遇到新的 Bug、尚未完善的機制以及需要重新審視的架構決策。

但 Steel 已經不再是一個「也許有一天能變成伺服器」的玩具原型了。它是一個你今天就能連線進去遊玩的伺服器，背後凝結了九個月的研發積累、經過嚴格測試驗證的原版地形生成相容、可正常運作的核心玩法系統，以及一群不斷壯大的貢獻者團隊。

最近我邀請了三位見習維護者加入團隊：Junky、Evald 和 purdze。我希望他們能共同推動專案前進，讓 Steel 不再過度依賴我一個人。這一點在當下尤為重要——因為我即將開始服兵役，在接下來大約一年的時間裡，能夠投入到專案中的時間會有所減少。不過大多數週末我依然會在線上審閱程式碼、解答問題，並盡己所能繼續開發。

這也是我選擇在此時正式公佈 Steel 的重要原因之一：這個專案需要成長為一個超越我個人默默耕耘的開源社群工程。

## 關於 AI 輔助貢獻的說明

Steel 允許將 AI 作為輔助工具使用，但絕不允許用它替代貢獻者自己的思考。無論你是用它查詢 API、理解編譯器錯誤，還是探討可行的實作思路，你都必須透徹理解自己提交的每一行程式碼，並能夠清晰地闡明背後的設計考量。

我們不接受完全由 AI 自主生成的 Pull Request，貢獻者必須親自撰寫並理解自己的 PR 描述。我們的[貢獻指南](/zh-tw/development/start-contributing/)詳細列出了相關規範與入門方式。
